## 구현과 상태 보존 범위

`features/shinhan-intake`는 네 유형의 구분된 초안, 공통 연락처·동의, 개인정보 진입·복귀를 제공한다. `app/shinhan/(intake)/layout.tsx`의 작은 Client Provider가 신청 미리보기와 개인정보 전문을 함께 감싸며 페이지 이동 중 초안을 유지한다. 본문·헤더는 Server Component이고 페이지에서 Server 요소를 슬롯으로 조합한다.

- 단계, 부분 입력을 포함한 문자열, 예산, 계약기간, 성별·주거 형태·가구 상태, 복수 걱정 선택, 필수 동의, 선택 동의의 미응답/동의/미동의를 보존한다.
- 개인정보 전문의 상단·하단 복귀 버튼과 브라우저 뒤로/앞으로 가기는 동일한 작성 상태로 돌아간다.
- 초안 시작 때 복귀 경로를 기록하여 본문 ‘전문 보기’와 푸터 전문 링크 모두 현재 초안으로 돌아온다. 열람은 동의를 변경하거나 제출하지 않는다.
- 신청 유형 버튼은 해당 유형의 새 빈 초안으로 시작한다. 이전 유형의 연락처·조건·동의를 복사하지 않는다.
- 상태는 현재 탭의 공유 layout 메모리에만 있다. URL·localStorage·sessionStorage에 개인정보를 기록하지 않는다. 새로고침과 새 문서 로드에서는 초기화한다. 초안 없이 전문에 진입하면 ‘홈으로 돌아가기’를 표시한다.
- 연락처는 입력 원문을 유지하고 Zod 검증 시에만 공백·하이픈을 정리한다. 휴대폰 형식과 필수 동의 오류를 각 필드에 표시한다.

`widgets/shinhan-privacy`는 Figma의 전문 6절과 신청별 수집 항목 5행을 구현한다. PC 본문 최대 960px, 모바일 좌우 20px, 단일 열 요약과 가로 넘침 없는 표를 적용했다. 공통 UI `TextField`, `Checkbox`, `SelectTile`, `BtnCta`와 기존 브랜드 에셋을 재사용했으며 새 에셋·의존성은 없다.

## 개발 화면과 운영 구분

개발 서버의 `/shinhan/dev/intake`에서 네 유형의 대표 필드와 **검증용 2단계**를 사용할 수 있다. 이는 실제 고객 신청 화면의 단계 구성을 확정한 것이 아니다. 실제 소개 화면의 신청 CTA는 아직 연결하지 않았다.

- 견적: 동·호수·침대 준비 상태. 기본 주소는 후속 단계의 기존 카카오 주소검색 연결 대상으로 남긴다.
- 방 등록: 자유 입력 위치·자가/월세·전세.
- 게스트 예산: 자유 입력 지역·20~100만 원의 1만 원 단위 예산. 초안에는 원 단위로 보관한다.
- 게스트 수요: 자유 입력 지역·1~12개월 및 별도 ‘12개월 이상’·성별.
- 등록을 제외한 유형에서 복수 선택과 선택 동의 보존을 확인한다. 실제 걱정/가이드 흐름은 후속 구현한다.

`/shinhan/dev/intake`와 `/shinhan/privacy`는 `NODE_ENV !== 'development'`일 때 `notFound()`로 차단한다. 푸터 전문 링크도 개발 환경에서만 활성화했다. 두 route는 검색 제외 metadata를 사용한다. 운영 빌드의 접근 차단은 이번에는 코드 검토로 확인했으며, 운영 서버 실행·배포는 하지 않았다.

‘입력 형식 확인’은 브라우저 내부 검증만 하며 성공 문구에 접수되지 않았음을 명시한다. 접수 버튼은 비활성 상태다. 예시 접수 응답을 생성하거나 저장 완료로 표시하지 않는다.

## 동의 전문의 남은 차이

Figma 원문에는 운영 승인·버전 정보가 없다. API의 `LOCAL_ONLY_REQUIRED_V1`, `LOCAL_ONLY_OPTIONAL_V1` 역시 로컬 테스트 전용이다. 화면 원문을 해당 API 버전 또는 운영 승인본과 동일한 문서로 매핑하지 않았으며 화면에 개발 확인용임을 표시했다.

Figma의 ‘호스트 예상 월세 산정’ 수집 항목에는 전화번호가 없지만 실제 API는 phone을 요구한다. 원문을 임의 수정하지 않았으며 운영 연결 전에 수집 항목 정합성과 승인된 전문·버전을 확정해야 한다. 선택정보 동의 전문과 서버 동의 snapshot/hash의 연결도 남아 있다.
