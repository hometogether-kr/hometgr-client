# 입주 희망 지역 요청 API 제안

상태: **백엔드 합의 전 제안**. 이번 작업은 프론트 시안과 명세 작성만 포함한다. 아래 경로는 현재 존재하거나 호출되는 API가 아니다.

## 현재 프론트

- S2의 지역명 입력은 Zod로 공백 제거 후 1~100자 검증한다.
- 빈 입력은 필드 오류를 표시하고 입력값은 보존한다.
- 유효한 입력은 온라인 접수 준비 중 안내를 표시한다. 네트워크 요청, 관리자 저장, 알림 발송, 가짜 성공 처리는 하지 않는다.
- 카카오 채널 추가 링크는 기존 제품 채널 `_BKlhX`를 재사용한다.

## 먼저 결정할 정책

1. 단순 지역 수요 집계인지, 개인에게 새 매물 알림까지 제공하는지 결정한다. 현재 Figma 문구는 개인 알림을 약속하지만 입력란에는 연락처가 없다.
2. 개인 알림을 제공한다면 로그인 회원의 확인된 연락 수단을 사용할지, 비회원 연락처·동의를 추가로 받을지 결정한다. 지역명만으로 알림 대상자를 알 수 없다.
3. 카카오 채널을 추가했다는 사실만으로 이 웹 요청과 카카오 사용자를 연결할 수 없다. 연동 식별 방식과 알림 동의/해지 정책이 별도로 필요하다.
4. 개인정보 항목·보관기간·삭제 정책과 관리자 접근 권한을 확정한다.

## 제안 계약: 로그인 기반 접수

`POST /guest-region-requests` (프론트는 기존 same-origin BFF를 사용)

인증된 회원 ID는 서버 세션에서 결정한다. 클라이언트가 회원 ID를 제출하지 않는다.

```json
{
  "regionText": "서울여대 근처",
  "source": "guest_landing"
}
```

- `regionText`: trim 후 1~100자, 자유 입력. 정규화한 지역 ID와 원문을 구분하여 저장한다.
- `source`: 허용된 고정 값으로 검증한다.
- `Idempotency-Key` 헤더: 재시도/더블 클릭으로 중복 레코드 생성 방지.
- 일정 시간 내 동일 회원·정규화 지역 중복 정책과 속도 제한을 서버에서 적용한다.

성공 `201` 예시:

```json
{
  "id": "<request-id>",
  "regionText": "서울여대 근처",
  "status": "pending",
  "createdAt": "2026-09-30T00:00:00.000Z"
}
```

오류: `400` 입력 오류, `401` 로그인 필요, `409` 정책상 중복, `429` 요청 과다, `5xx` 저장 실패. 기존 API 오류 envelope에 맞추고 필드 오류는 `regionText`에 매핑한다. 실제 응답 구조와 상태 코드는 백엔드와 확정해야 한다.

## 관리자 기능 제안

- `GET /admin/guest-region-requests`: 페이지네이션, 지역 검색, 처리 상태, 접수 기간 필터.
- `PATCH /admin/guest-region-requests/:id`: 처리 상태(`pending`, `reviewing`, `completed`, `closed`)와 내부 메모 변경.
- 관리자 인가·변경 감사 기록 적용. 일반 회원에게 요청 목록/연락처가 노출되지 않도록 한다.
- 개인 알림을 제공한다면 동의한 연락 수단, 알림 전송 상태/시점/실패 이력을 별도로 관리한다. `completed` 상태만으로 실제 알림 발송 완료를 가정하지 않는다.

## 프론트 후속 연결

1. `features/request-guest-region/api/`에 확정 요청과 Zod 응답 스키마 작성.
2. 폼 값 `region`을 API 입력 `regionText`로 명시적으로 변환.
3. mutation hook으로 pending/success/error를 표현하고 `BtnCta.loading`으로 중복 제출 방지.
4. 서버가 저장 성공을 확인한 후에만 접수 완료 표시. 실패 시 입력 유지·재시도 허용.
5. 인증 정책에 맞춰 로그인 후 요청 초안을 안전하게 복원.
6. 관리자 목록에서 실제 접수 확인까지 통합 검증. 운영 데이터에 테스트 요청을 남기지 않는다.
