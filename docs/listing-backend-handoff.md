# 백엔드 전달사항 — 매물 등록·입주자 메인

2026-10-01. 전달용 문서 작성 완료 / 외부 발송 및 API 구현 전.
상세 설계 초안: [API 변경 명세](listing-api-change-spec.md). 이 문서는 최신 사용자 주석을 반영한 범위와 우선순위를 요약한다.

## 요청 목적 및 진행 순서

실매물 한 건이 등록 → 관리자 검수 → 게시 → 메인·탐색 카드·상세에서 일관되게 표시되도록 한다. 백엔드 계약 제공과 프런트 작업 후 dev에 실매물 2~3개를 등록하여 확인한다. 이후 검색·지도·디자인 최종 검증·전체 이관을 진행한다. addressRegion 누락 상세 오류 수정은 별도 보류다.

## 우선 구현 요청

| 항목           | 요청                                                                                                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 유형           | buildingType을 apartment/officetel/detachedHouse/shareHouse로 통일하는 안. 기존 villa/other는 임의 변환하지 말고 호환·검수 계획 제공                                          |
| 지역           | 시도·시군구·읍면동·법정동 코드를 보존. region 중첩 필드 및 서버 코드 검증안은 API 명세 참고. 공급자·복합 행정구역 매핑은 기술 협의 필요                                       |
| 제목           | 서버에서 지역+유형 자동 생성. 예: **노원구 공릉동의 아파트**. 건물 동·호수는 제목에 포함하지 않음                                                                             |
| 거주 인원      | residentCount 정수 0~100으로 확장. 0명이면 residentType/residentGenderComposition은 해당 없음. null 표현 제안. 1명 이상이면 기존 enum 필수. autosave·완료 저장·응답 모두 적용 |
| 입주 가능 인원 | roomCapacity one/two/threeOrMore 재사용. 현재 거주 인원과 별개. threeOrMore를 3으로 변환하지 않음                                                                             |
| 면적           | household.areaRange를 집 전체 전용면적으로 상세에 반환. 기존 범위 유지, 정확한 ㎡ 추가 불필요                                                                                 |
| 소제목         | nullable subtitle 저장 필드와 관리자 검수 시 편집 API 추가. 1~100자 trim, null 삭제, 생략/공백 거부는 제안. 기존 매물 설명·가격에 영향 없어야 함                              |
| 집주인 소개    | User.introduction 재사용. 일반 회원용 host 응답에 필요한 공개 프로필만 매핑                                                                                                   |
| 주소·가격      | 임시저장과 제출·게시를 구분. 최종 제출·게시 정확 주소/가격 필수 정책 유지. 동·호수는 저장하되 일반 회원에게 반환하지 않음                                                     |

## 응답 공개 기준

- 비회원: 동 단위 지역까지만 주소 공개. 상세 계약정보·정확 위치·집주인 정보 비공개.
- 일반 회원: 도로명 주소·건물 수준 위치·층수 공개. **건물 동·호수는 예약 상태와 관계없이 일반 공개 상세 응답에서 제외**한다. 계약 업무용 별도 전달 경로는 이 문서에서 변경하지 않는다.
- owner/admin 업무용 상세는 권한 검사 후 원본 주소를 조회할 수 있게 기존 책임을 유지한다. 일반 회원 응답과 serializer를 분리한다.
- addressDetail 문자열에서 호수만 지우는 방식 대신 필드 자체를 제외한다. 건물 동 정보가 섞인 다른 주소·설명·제목·지도 데이터도 공개 경로를 점검한다. 위도·경도는 특정 세대나 개별 동을 식별하는 수준으로 보내지 않는다.
- 프런트에서 가리는 것만으로 처리하지 않는다. 서버 초기 데이터와 인증별 캐시에서도 정책을 적용한다.
- 관리자 주소 숨김 UI는 당장 불필요하다. 기존 API·저장 필드는 삭제하지 않는다. 기존 true 값을 자동 해제하지 않는다. 일반 회원의 동·호수 비공개는 해당 플래그와 무관하게 적용한다.
- 비회원 사진·목록 가격·소제목 등 나머지 노출은 이전 제안이며 명시 확정 전 기존 정책을 임의로 확대하지 않는다. 필요한 필드별 응답 예시를 먼저 회신한다.

## API 계약 제안

기존 draft PUT/autosave/GET/submit, host/admin 상세, 공개 목록·상세, 관리자 승인 경로를 함께 맞춘다. expectedVersion 및 기존 소유권·상태 검증은 유지한다.

소제목 단독 API 제안:

```http
PATCH /admin/rooms/:id/subtitle
Content-Type: application/json

{"subtitle":"공릉역 도보 7분"}
```

200 응답: `{ "id": "UUID", "subtitle": "공릉역 도보 7분" }`. room/super 관리자만 수정. 기존 가격 필수 PATCH에 소제목만 보내지 않는다. 소제목 미입력 게시 허용·최대 100자는 설계 제안으로 계약 확정 시 명시한다.

목록 응답에 title/subtitle/buildingType/region/residentCount/roomCapacity를 연결하고, v2 상세는 기존 data.household/data.preferences 구조를 재사용한다. legacy/null과 v2 discriminator 호환을 유지한다. 임의로 누락값을 0이나 다른 유형으로 채우지 않는다.

## 이번 확정 구현에서 제외 / 기술 결정 필요

- 자유 검색 q의 대상과 학교·역 연관 방식: 사용자 결정 보류. 지역·제목 검색도 확정된 기능으로 구현하지 않는다. 구조화된 지역 저장은 먼저 진행 가능.
- 관리자 면적 보완: 주소를 검색해 확인한 면적을 관리자 입력하는 방안 검토 중. 채택 시 기존 areaRange 수정 및 근거 기록 제안. 이번에는 새 면적 수정 API를 필수 요청하지 않는다.
- 층수: 회원 공개는 확정. 등록 시 302호→3, 1602호→16, B101호→-1 자동 추정 후 확인·수정은 제안. 저장 필드·허용 범위·필수 여부를 확정한 후 구현한다.
- 신규 정렬: 최초 게시일 최신순은 제안이며 createdAt과 구분해 계약을 확인한다.
- 인증 배지·전체 노션 이관·S2 지역 요청은 별도 작업.

## 백엔드 회신 요청 및 완료 기준

1. 최종 필드명/enum/nullable 규칙, 변경 endpoint, DB 변경 및 legacy·기존 draft 처리 계획.
2. 0명/1명 이상 household, 소제목 저장·삭제, 익명/회원/owner/admin 상세, 목록 응답의 JSON 예시.
3. 서버 반영 시점과 구버전 클라이언트 호환 기간. 회원 동·호수 비공개 응답부터 안전하게 배포.
4. 실매물 2~3개를 dev에 호스트 등록 → 관리자 소제목 검수 → 승인 → 목록·상세에서 동일 값 확인.
5. 이번 사용자 실매물 테스트에서 주소·가격 누락 시나리오는 제외한다. 필수값 검증 로직 자체를 삭제하는 요청은 아니다.

미확정 항목 때문에 기존에 확정된 인원·면적·소제목 작업 전체를 막을 필요는 없다. 다만 미확정 제안을 승인된 제품 정책으로 구현하지 않는다.
