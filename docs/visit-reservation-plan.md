# 방문 예약 개발 계획

기준일: 2026-10-20 · 사용자 합의 반영본

기존 프론트 화면과 API를 최대한 활용해 방문 신청, 확정, 취소 후 재신청, 자동 방문 완료, 후기 저장까지 연결한다. PM·프론트는 정책과 화면 요구사항을 정리하고, 백엔드는 기존 시스템을 확인해 OpenAPI 초안을 제안한다. 프론트는 화면에 필요한 정보와 행동을 기준으로 리뷰한다.

이번 문서는 사용자와 확정한 정책을 반영한다. 제품 코드와 개발 서버는 변경하지 않는다. 구현 현황에 대한 기존 관찰은 참고 자료이며, 최신 서버·관리자·배포 환경을 이번 작업에서 검증한 것은 아니다.

## 공통 정책

### 개발 범위와 협업 방식

- PM은 프론트를 담당한다. 수정 저장소는 hometgr-client이며 백엔드·관리자은 담당자에게 요구사항을 전달한다.
- 문서는 공통 정책, 화면별 요구사항, 미결정 사항과 백엔드 확인 목록으로 구성한다.
- 백엔드는 기능별로 기존 그대로 사용 / 기존 API 보완 / 신규 필요 / 확인 필요를 구분한다. API 경로·DTO·DB 구조·내부 상태 이름을 이 문서에서 고정하지 않는다.
- 관리자 업무는 기존 reservation 탭에 연결한다. 별도의 예약 관리 시스템을 만들지 않는다.
- 계약·결제·정산, 공개 후기, 호스트 가용 시간표, 대리 신규 예약 생성은 이번 범위에서 제외한다.
- 패널티는 추후 검토로 넘긴다. 패널티를 위한 기능·집계·별도 운영 절차를 추가하지 않는다.
- 정기 전화 확인·전화 확인 기록, 신규 알림 재시도·재발송 기능, 신규 연락 가능 시간 관리 기능은 만들지 않는다.

진행 순서는 정책 합의 → 기존 API·관리자 확인 → 백엔드 OpenAPI 초안 → 프론트 화면 리뷰 → 계약 확정 → 담당자별 개발 → 통합 확인이다. 백엔드 확인 목록은 문서 마지막에 포함했다. 이 문서 작성은 외부 담당자에게 실제 메시지를 발송한 것을 의미하지 않는다.

### 이번 개발의 완료 기준

> 실제 입주자가 신청한 예약을 호스트가 확정하고, 변경·취소 또는 확정된 방문 일시에 따른 자동 완료까지 양쪽에서 같은 정보로 확인할 수 있다. 이후 입주자가 후기를 저장하고 관리자가 확인할 수 있다.

일반 사용자의 일정 변경은 취소 후 재신청으로 처리한다. 관리자는 상담 결과에 따라 합의한 일정을 직접 반영하거나 상태를 정정할 수 있다. 자동 완료는 실제 방문 여부를 검증했다는 의미가 아니다.

### 최초 신청과 확정

1. 로그인한 입주자가 예약 가능한 매물에서 신청한다. 서버도 역할·매물·중복 신청 권한을 확인한다.
2. 신청 다음 날부터 14일간 서로 다른 후보 시간 1~3개를 선택한다. 10월 20일 신청이면 10월 21일~11월 3일이다.
3. 제출하면 승인 대기가 된다. 호스트 목록에도 표시하되 확정 일정은 아직 없다.
4. 호스트가 유효한 후보 하나를 선택해 수락하면 즉시 방문 예약 확정이다. 입주자의 추가 승인은 없다.
5. 거절하는 경우 사유를 전달한다. 모든 후보가 어려우면 홈투게더 카카오 상담으로 일정 조율을 돕는다.

호스트 화면에서는 승인 대기와 예약 확정을 구분한다. 예정된 방문에 확정 예약만 표시하더라도 신청 대기 내역은 같은 예약 관리 화면에서 확인할 수 있어야 한다. 별도 새 페이지보다 기존 목록의 상태 표시·필터를 활용한다.

### 취소 후 재신청으로 일정 변경

일정 변경은 기존 예약 취소 후 같은 매물에 다시 신청하는 방식으로 통일한다. 별도의 변경 승인 대기 상태를 만들지 않는다.

1. 입주자가 기존 화면의 예약 변경 버튼을 누른다.
2. 기존 확정 일정을 보여주고, 기존 예약이 취소되며 새 일정은 호스트 수락 후 확정된다고 안내한다.
3. 입주자가 확인하면 기존 예약을 취소한다. 취소가 성공한 뒤 같은 매물의 방문 시간 선택 화면으로 이동한다.
4. 새 후보 1~3개를 제출한다. 이후는 최초 신청과 동일하다.
5. 신청을 중단하거나 새 신청이 거절·만료되어도 기존 확정 일정은 복구되지 않는다.

취소가 실패했다면 취소된 것처럼 안내하거나 새 신청을 진행하지 않는다. 취소 후 새 신청 실패 시에는 기존 취소 결과를 명확히 보여주고 다시 신청할 수 있게 한다. 화면 재사용과 서버 내부 기록의 생성·재사용 방식은 별개이며, 번호·이력 설계는 백엔드가 제안한다.

호스트가 먼저 일정을 바꾸려는 경우에도 직접 새 날짜를 고르지 않는다. 사유를 입력해 취소하고 입주자가 재신청하거나 관리자 상담으로 대응한다. 호스트가 고를 수 있는 시간은 입주자가 제출한 유효 후보뿐이다.

기존 안의 변경 요청만 만료, 기존 일정 유지, 변경 승인 대기 중 방문 시각 도래, 대기 중 후보 교체·기한 갱신 규칙은 취소 후 재신청 정책으로 대체되었다. 해당 상태·API·화면은 이번 요구사항에서 제외한다.

### 변경·취소 기한과 재방문

입주자와 호스트의 직접 변경·취소는 한국 날짜 기준 방문일 2일 전까지다. 방문일 이틀 전 23:59:59까지 허용하며, 금요일 방문이면 수요일까지 가능하다. 목요일부터는 관리자 상담으로 연결한다. 응답 기한인 48시간과 다른 기준이다.

새 신청은 제출 시점부터 응답 기한을 새로 계산한다. 새 후보 기간도 새 신청일 다음 날부터 14일이다. 기존 예약 취소 기한을 넘긴 상태에서는 재신청을 위한 직접 취소도 허용하지 않는다.

재방문은 횟수 제한 없이 허용한다. 사용자 화면에서 최초 방문·재방문 유형을 따로 나누거나 별도 재방문 번호를 요구하지 않는다. 취소·거절·완료 후 동일한 신청 흐름을 이용한다. 다만 같은 입주자·매물에 진행 중인 신청 또는 확정 예약은 하나만 허용한다. 이는 다른 입주자의 같은 매물 신청을 막는 규칙이 아니다.

### 응답 기한과 자동 완료

| 상황 | 확정된 처리 기준 | 화면·알림 결과 |
| --- | --- | --- |
| 최초 신청 또는 취소 후 새 신청 | 신청 시각 + 48시간과 마지막 후보 시각 중 먼저 도달한 시점에 자동 취소 | 입주자·호스트에게 취소 결과 안내 |
| 일부 후보 시각 경과 | 지난 후보는 선택 불가. 미래 후보가 있고 48시간이 지나지 않았다면 신청 유지 | 호스트에게 남아 있는 후보와 실제 응답 마감 표시 |
| 유효 후보 수락 | 선택한 후보로 즉시 확정 | 양쪽에 같은 확정 일정 표시 |
| 확정 예약의 방문 시각 도래 | 자동 방문 완료 | 후기 작성 가능 |
| 이미 취소·거절된 예약 | 자동 완료하지 않음 | 종료 상태와 사유 유지 |

마감 시각에 도달하면 더 이상 수락할 수 없다. 호스트가 신청을 열어봤다고 응답 기한이 늘어나지 않는다. 예를 들어 월요일 10시 신청, 마지막 후보가 화요일 14시면 화요일 14시에 취소된다. 마지막 후보가 금요일이면 수요일 10시에 취소된다.

실제 응답 마감, 방문 시각, 가능한 행동은 서버 기준으로 일관되게 제공한다. 만료·수락·취소·자동 완료가 겹쳐도 하나의 유효한 결과로 처리하도록 백엔드가 제안한다. 자동 완료는 방문 시작 시각 기준이며 방문 종료 확인을 요구하지 않는다.

### 관리자 상담과 예외 처리

관리자는 기존 reservation 탭에서 예약을 찾아 당사자들이 합의한 날짜·시간을 입력하고 바로 확정할 수 있다. 호스트·입주자의 화면에 동일한 결과를 반영하고 양쪽에 알림톡을 보낸다. 관리자에게 알림톡을 보내지 않는다.

| 관리자 작업 | 확정 범위 |
| --- | --- |
| 기존 예약에 일정 입력·확정 | 양쪽 합의를 확인한 후 직접 반영 |
| 변경·취소 기한 이후 요청 | 상담 결과에 따라 일정 변경 또는 취소 가능 |
| 자동 완료 후 미방문 등 문의 | 확인 후 취소로 정정하거나 합의한 새 일정으로 변경 가능 |
| 처리 기록 | 처리 사유를 짧게 남기고 처리자·시각은 자동 기록 |
| 예약이 없는 고객의 대리 신규 예약 | 이번 범위에서 보류. 입주자가 먼저 신청하도록 안내 |

정기 전화 확인이나 별도 전화 확인 기록은 만들지 않는다. 일반 사용자에게 적용되는 기한이 관리자 상담 후 예외 처리를 막지 않게 한다. 동일 입주자·매물에 다른 진행 예약이 있거나 이미 후기가 있는 기록을 정정할 때의 데이터 보존·충돌 처리안은 백엔드 초안에서 검토한다. 확정하지 않은 세부 동작을 임의로 구현하지 않는다.

### 후기 정책

- 자동 방문 완료 처리와 동시에 후기 작성이 가능하다. 실제 방문을 마친 후 작성해 달라고 안내한다.
- 방문당 1회 작성 가능하며 수정할 수 없다. 재방문은 허용하므로 이전 후기와 현재 방문의 작성 여부를 구분할 수 있어야 한다.
- 기존 두 평가 항목인 집주인 소통·매물 설명 일치 각각 1~5점으로 한다.
- 상세 후기는 앞뒤 공백 제외 10~1,000자로 확정한다. 프론트와 서버에 같은 검증 기준을 적용한다.
- 이번에는 저장과 관리자 조회만 제공한다. 공개 후기와 후기 요청 알림톡은 보류한다.
- 자동 완료와 후기 작성은 실제 방문 검증을 의미하지 않는다. 전화 확인은 작성의 선행 조건이 아니다.

### 예약 번호와 방문 이력

입주자·호스트는 예약 번호를 확인·복사하고 관리자는 reservation 탭에서 검색한다. 사용자에게 재방문을 별도 예약 유형이나 별도 번호 체계로 구분하도록 요구하지 않는다.

번호 형식·발급·재사용과 내부 기록 식별 방식은 백엔드가 제안한다. 사용자에게 보이는 예약 번호와 내부 방문 이력 식별은 구분해 설계할 수 있다. 별도의 신규 번호 발급을 기획에서 강제하지 않는다. 이전 방문·취소 사유·후기를 덮어쓰지 않고 방문당 후기 1회를 보장해야 한다. 서로 다른 입주자의 기록과 조회 권한도 분리한다.

### 주소와 연락 정보 공개

| 상태 | 공개 기준 |
| --- | --- |
| 비회원 | 사진·주소 비공개, 로그인 안내 |
| 로그인 후 신청 전·승인 대기 | 동네·주변 역 등 대략적인 위치 |
| 예약 확정 | 예약 당사자에게 방문에 필요한 상세 주소와 안내 |

관리자가 합의한 일정으로 확정한 예약에도 같은 기준을 적용한다. 알림톡에는 상세 주소를 직접 넣기보다 예약 확인 링크로 연결한다. 로그인만으로 타인의 예약·상세 주소를 볼 수 없어야 한다. 취소·완료 기록에서의 상세 주소 반환 범위는 기존 권한 정책을 확인해 OpenAPI 초안에 제안한다.

집주인 연락 가능 시간은 기존 정보가 있을 때만 표시한다. 없으면 항목을 생략한다. 별도의 입력·수정 기능이나 신규 수집은 만들지 않으며, 정보가 없어도 예약은 진행할 수 있다.

### 알림톡과 관리자 페이지 연결

알림 채널은 알림톡이다. 행동한 본인에게 접수·처리 확인을, 상대방에게 필요한 안내를 보낸다. 관리자에게는 보내지 않는다.

| 사건 | 입주자에게 | 호스트에게 |
| --- | --- | --- |
| 최초 신청·취소 후 새 신청 | 신청 접수 확인 | 후보 확인·수락 요청 |
| 호스트 수락 | 확정 일정·예약 확인 | 처리 완료 확인 |
| 입주자 취소 | 취소 결과 확인 | 취소 결과·사유 |
| 호스트 취소·거절 | 결과·사유·재신청 또는 상담 안내 | 처리 완료 확인 |
| 무응답·후보 만료 자동 취소 | 취소 결과 | 취소 결과 |
| 관리자 일정 반영·취소·상태 정정 | 처리 결과와 현재 일정·상태 | 처리 결과와 현재 일정·상태 |
| 방문 리마인드 | 전날·당일 방문 안내 | 전날·당일 방문 안내 |

취소 후 재신청에서는 취소 결과와 새 신청 접수를 각각 안내한다. 별도의 변경 요청·변경 승인 대기 알림은 만들지 않는다.

#### 방문 리마인드

- 수신 대상은 입주자와 호스트 양쪽이다.
- 한국 시간 기준 방문 전날 오후 6시, 방문 당일 방문 시각 2시간 전에 발송한다.
- 금요일 오후 2시 방문이면 목요일 오후 6시와 금요일 낮 12시에 발송한다.
- 발송 시점이 지난 뒤 확정된 예약은 지난 리마인드를 생략한다. 예약 확정 알림은 정상 발송한다.
- 취소되면 남은 발송을 중단한다. 관리자가 일정을 바꾸면 이전 발송을 중단하고 새 일정의 미래 발송 시점만 적용한다.
- 자동 완료를 이유로 별도의 후기 요청 알림톡을 보내지 않는다.

#### 매물 등록 알림

- 호스트 제출 성공 시 등록 접수 알림톡을 보낸다. 임시저장은 제외한다.
- 관리자 검토 후 실제 공개 게시 시 게시 완료 알림톡을 보낸다. 단순 관리자 접수와 구분한다.

#### 기존 관리자 페이지에서 알림 연결

알림톡은 기존 관리자 페이지에서 연결할 예정이다. 기존 기능을 우선 활용하며 재시도·재발송 기능이나 별도 발송 관리 화면은 새로 만들지 않는다. 알림 실패로 성공한 예약 처리를 되돌리거나 실패로 표시하지 않는다.

관리자 페이지에서 신청·확정·취소·일정 정정과 알림을 연결할 수 있는지 확인한다. 방문 리마인드도 현재 예약 상태와 일정을 기준으로 발송하고, 취소되거나 일정이 바뀌면 남은 발송에 반영한다.

#### 로그인 후 예약 화면 복귀

알림톡 → 해당 역할의 예약 상세 → 필요하면 로그인·온보딩 → 원래 예약 상세로 복귀한다. 기존 프론트의 returnTo 보존 코드를 활용한다. 실제 알림톡·카카오 인앱 브라우저·온보딩 경로는 통합 확인이 필요하다. 다른 계정으로 로그인했다면 예약 정보를 공개하지 않는다.

## 화면별 요구사항과 필요한 데이터

아래 정보는 화면에서 사용할 내용이며 API 필드명이 아니다. 백엔드는 공통 예약·매물·상대방 요약을 묶어 응답을 제안한다. 목록 카드마다 매물·호스트 API를 추가 호출하지 않아도 되도록 하되, 역할별 비공개 정보는 분리한다.

### 정보 없음·비공개·실패의 구분

사진 자체가 없으면 대체 이미지를, 권한 때문에 비공개면 로그인 또는 공개 조건 안내를, 권한이 있지만 조회에 실패하면 다시 시도를 제공한다. 세 경우를 같은 빈 값으로 숨기지 않는다. 비회원 사진 비공개는 기존 매물 미리보기와 차이가 있을 수 있으므로 적용 범위를 확인한다.

### G01 매물 상세에서 예약 진입

목적: 로그인 상태에 따라 예약 신청 또는 로그인으로 안내한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 로그인 여부 | 로그인 상태면 방문 예약 신청 화면으로 이동. 비회원이면 로그인 안내 메시지 표시 |

### G02 방문 시간 선택과 취소 후 재신청

목적: 최초 신청·재신청·재방문에 기존 시간 선택 화면을 사용한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 선택한 매물 식별 정보 | 같은 매물의 예약 신청 |
| 매물 제목·부제목·월세·보증금·대표 사진 | 신청할 매물 확인 |
| 선택 가능한 기간·시간대 | 다음 날부터 14일의 후보 선택 |
| 최대 선택 개수 3개·선택한 후보 | 1~3개 확인 후 제출 |
| 신청 가능 여부·제출 결과 | 중복·권한·매물 상태 변경 또는 저장 실패 안내 |

기존 예약 번호·확정 일정은 취소 전 확인 화면에서 사용한다. 새 시간 선택 화면에서 변경 후보를 기존 확정 일정과 함께 유지하지 않는다. 취소 성공 후 새 신청을 중단해도 기존 일정이 복구되지 않는다는 안내가 필요하다.

### G03 입주자 예약 목록

목적: 현재 상황과 다음 행동을 한눈에 확인한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·상세 연결 | 예약 식별·상담·상세 진입 |
| 매물 제목·부제목·대표 사진, 호스트 표시 이름 | 집과 상대방 확인 |
| 신청한 후보·유효 여부·응답 마감 | 확정 전 신청 내용 표시 |
| 확정 일정·상태 | 승인 대기·예약 확정·방문 완료·거절/취소 표시 |
| 현재 방문의 후기 작성 여부·가능한 행동 | 변경·취소·후기 버튼 표시 |

신청한 후보 시간과 신청서를 제출한 시각을 혼동하지 않는다. 재방문은 별도 유형으로 나누지 않되 이전 기록·후기를 덮어쓰지 않는 목록 표현을 백엔드와 맞춘다.

### G04 입주자 예약 상세와 취소 확인

목적: 방문 정보 확인, 취소 또는 취소 후 재신청을 진행한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·상태·가능한 행동·처리 기한 | 진행 상황과 버튼 표시 |
| 호스트 정보·기존 연락 가능 시간 | 상대방 확인. 연락 시간이 없으면 생략 |
| 매물 제목·부제목·대표 사진 | 방문할 집 확인 |
| 공개 범위에 맞는 위치·주소 | 대략적인 위치 또는 확정 후 상세 주소 |
| 후보·응답 마감 또는 확정 일시 | 신청·확정 상태에 맞는 일정 표시 |
| 취소·거절 사유와 처리 주체 | 종료된 이유 안내 |

예약 변경 버튼은 기존 일정 취소 확인 → 취소 성공 → 같은 매물 신청 화면으로 연결한다. 기한 이후에는 관리자 상담으로 안내한다. 별도의 변경 대기 화면은 없다.

### G05 방문 후기 작성

목적: 현재 방문에 대해 한 번만 작성한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·현재 방문을 식별하는 정보 | 후기 저장 대상 연결. 내부 식별 방식은 백엔드 제안 |
| 매물 제목·부제목·대표 사진·호스트명 | 평가할 집과 호스트 확인 |
| 자동 완료 여부·현재 방문의 작성 여부 | 작성 가능·기작성 표시 |
| 저장 결과 | 중복 제출 방지와 완료 안내 |

두 평가 항목 각 1~5점, 상세 후기 앞뒤 공백 제외 10~1,000자다. 실제 방문 후 작성 안내를 표시한다. 저장 후 수정 불가이며 공개·후기 요청 알림톡은 보류한다.

### H01 호스트 예약 목록

목적: 승인 대기 신청과 확정 방문을 함께 관리한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·매물 요약 | 신청 식별 |
| 입주자 표시 이름·기존 자기소개 요약 | 방문 상대 확인 |
| 유효한 후보·실제 응답 마감 | 승인 대기 신청 대응 |
| 확정 일정·상태·가능한 행동 | 확정 방문과 종료 내역 구분 |

승인 대기 신청은 확정 일정이 없어도 목록에 표시한다. 기존 예시 데이터를 실제 조회로 교체한다. 

### H02 호스트 예약 상세와 취소 사유

목적: 후보 수락·거절 또는 확정 예약 취소를 처리한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·매물·입주자 요약 | 신청 내용 확인 |
| 유효 후보·응답 마감 | 후보 하나를 골라 수락 |
| 확정 일정·직접 취소 기한 | 확정 방문 확인 및 취소 가능 여부 |
| 거절·취소 사유 | 입주자에게 결과와 대응 방향 전달 |
| 관리자 상담 경로 | 후보가 모두 어렵거나 기한이 지난 경우 상담 |

호스트가 새 날짜를 직접 입력하는 기능은 제공하지 않는다. 변경이 필요하면 사유를 입력해 취소하거나 상담한다. 수락 성공 시 입주자와 호스트 화면에 선택한 같은 일정이 표시되어야 한다.

### A01 관리자 reservation 목록

목적: 상담 대상 예약을 빠르게 찾는다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호 | 검색 |
| 매물·입주자·호스트 요약 | 대상과 당사자 확인 |
| 후보 또는 확정 일정·현재 상태 | 조율·정정 대상 파악 |

기존 목록·필터를 최대한 활용한다. 정기 전화 확인 대기 목록이나 패널티 관리를 추가하지 않는다.

### A02 관리자 reservation 상세

목적: 합의 일정 반영과 상담에 따른 예외 처리를 한다.

| 필요한 정보 | 화면에서 사용하는 곳 |
| --- | --- |
| 예약 번호·당사자·매물 정보 | 상담 대상 확인 |
| 현재 후보·확정 일정·사유 | 합의한 일정 입력·확정 또는 취소 |
| 이전 방문·취소·정정 이력 | 기존 기록을 보존하며 경위 확인 |
| 작성된 후기와 연결 방문 | 내부 후기 조회 |
| 처리 사유·처리자·시각 | 사유 입력과 자동 기록 |

관리자는 기한 이후에도 일정 변경·취소·완료 상태 정정을 할 수 있다. 대리 신규 예약 생성은 보류한다. 자동 완료를 매번 수동 승인하지 않는다. 정정 이후 현재 일정·상태와 알림 예약이 일치해야 한다.

### N01 알림톡에서 해당 화면으로 이동

목적: 수신자가 자신의 예약을 확인하고 행동한다.

| 필요한 정보 | 사용하는 곳 |
| --- | --- |
| 사건·수신 역할·연락처 | 접수·처리·리마인드 문구와 수신 대상 |
| 예약 번호·필요한 일정 | 알림 내용 |
| 역할별 예약 확인 링크·로그인 복귀 경로 | 로그인·온보딩 후 원래 화면으로 이동 |

상세 주소는 예약 화면에서 권한 확인 후 보여준다. 이미 취소된 예약 링크는 최신 상태를 보여주고, 다른 계정은 예약 정보를 볼 수 없게 한다. 후기 요청 링크 발송은 이번 범위에서 제외한다.

### OpenAPI 초안 리뷰 기준

- G01~G05, H01~H02, A01~A02, N01별로 필요한 정보와 행동이 응답 예시에 포함되어야 한다.
- 목록·상세에 공통 예약, 매물, 상대방 요약을 재사용하되 역할별 공개 범위는 지켜야 한다.
- 목록 카드마다 추가 API 호출 없이 화면을 그릴 수 있어야 한다. API 개수를 줄이기 위해 무관한 기능을 하나로 합치지는 않는다.
- 취소 후 재신청에 기존 취소·신청 API를 활용할 수 있는지 먼저 검토한다. 별도 변경 대기 API는 요구하지 않는다.
- 상태별 가능한 행동, 실제 응답 마감, 확정 일정, 거절·취소 사유, 현재 방문의 후기 작성 여부를 화면에서 판단할 수 있어야 한다.
- 권한 없음·중복 진행 예약·이미 처리됨·기한 경과·매물 예약 불가·저장 실패를 구분해 설명할 수 있어야 한다.
- 예약 성공과 알림 발송 실패가 분리되어야 한다. 관리자 페이지의 알림 연결 및 취소·일정 정정 후 리마인드 동작을 확인해야 한다.

사용자 흐름과 주요 운영 정책은 위 내용으로 확정했다. 아래는 구현 방식을 제안받거나 기존 시스템을 확인할 항목이며, 폐기된 변경 대기 정책을 다시 결정할 목록이 아니다.

### 백엔드 전달 요청문

확정된 공통 정책과 화면 요구사항을 기준으로 기존 API와 관리자 reservation 탭·알림톡 연결을 먼저 확인해 주세요. 기존 API로 가능한 부분과 보완·추가가 필요한 부분을 확인해 주세요.

새 API를 정하기 전에 기존 신청·조회·수락·거절·취소 기능을 얼마나 활용할 수 있는지 확인해 주세요. 공통 응답을 활용해 프론트가 목록·상세를 효율적으로 그릴 수 있게 하고, 역할별 권한과 개인정보 공개 조건은 분리해 주세요. 변경 승인 대기 기능은 필요하지 않습니다.

결과물은 화면별 응답 예시를 포함한 OpenAPI 초안, 필요한 기존 API 보완·추가 제안, 관리자 페이지 연결안과 추가 결정이 필요한 질문 목록입니다. 확인되지 않은 부분은 구현 가능으로 단정하지 말고 확인 필요로 표시해 주세요.

### 서버·관리자 확인 체크리스트

#### 서버 처리와 데이터

- 후보의 한국 날짜 범위·중복·개수·지난 시각을 서버에서도 검증할 수 있는가? 선택 가능한 시간대의 기존 기준은 무엇인가?
- 실제 마감을 신청 시각 + 48시간과 마지막 후보 시각 중 빠른 값으로 제공하고 집행할 수 있는가? 호스트 열람 후에도 적용되는가?
- 수락 시 선택 후보를 확정 일정으로 저장·반환하고, 마감·취소·완료 처리와 충돌하지 않는가?
- 같은 입주자·매물의 진행 신청·확정 예약만 중복 제한하고 취소·거절·완료 후 신청을 허용하는가?
- 번호를 어떻게 표시·검색하고 과거 방문·취소·후기를 어떻게 보존할 것인가? 화면에 재방문 유형이나 별도 번호를 강요하지 않는가?
- 후기 두 별점 1~5점과 앞뒤 공백 제외 10~1,000자를 일치시키는가? 글자 수 계산 기준도 프론트와 맞는가?
- 상세 주소를 로그인만으로 반환하지 않고 확정·당사자 권한까지 확인하는가? 취소·완료 후 반환 범위는 초안에 명시했는가?
- 시간이 없는 과거 수락 데이터 등 기존 자료의 전환·제외 기준은 무엇인가? 근거 없이 자동 완료하지 않는가?

#### 관리자 reservation 탭

- 기존 목록에서 번호 검색과 당사자·매물·상태 확인이 가능한가?
- 합의 일정 입력·확정 및 기한 이후 취소·완료 정정에 필요한 최소 확장은 무엇인가?
- 정정 사유·처리자·시각을 기존 이력 기능으로 남길 수 있는가?
- 정정 대상에 이미 후기가 있거나 같은 매물의 다른 진행 예약이 있으면 기존 기록을 보존하며 어떻게 처리할 것인가? PM 결정이 필요한 부분은 무엇인가?
- 변경 결과가 양쪽 화면과 리마인드 예약에 함께 반영되는가?

#### 관리자 페이지 알림 연결

- 신청·확정·취소·관리자 일정 정정 결과를 입주자와 호스트의 알림톡에 연결할 수 있는가?
- 양쪽에 전날 18시·방문 2시간 전 리마인드를 발송하고, 취소·일정 정정을 반영할 수 있는가?
- 지난 발송 시점은 생략하고, 알림 실패가 성공한 예약 처리를 실패로 바꾸지 않게 할 수 있는가?
- 기존 기능을 활용하고 재시도·재발송 기능을 새로 만들지 않는가?
- 매물 제출 시 등록 접수, 실제 게시 시 게시 완료 알림을 연결할 수 있는가?

#### 프론트와 함께 확인

- 역할별 예약 링크가 로그인·온보딩 후에도 보존되는가? 다른 계정·취소된 예약 링크에 올바른 결과를 보여주는가?
- 기존 연락 가능 시간 필드가 있는가? 없다면 신규 수집 없이 생략하는가?
- 비회원 사진 비공개 정책과 기존 매물 미리보기 간 차이는 어느 화면을 수정해야 하는가?
- 공통 요약 응답으로 목록을 완성할 수 있는가? 역할별 비공개 데이터가 섞이지 않는가?
