# 신한 고객 프론트 11단계 — 호스트 방 등록 API 연결 준비

작성일: 2026-10-23 (Asia/Seoul). 기준 커밋 `7de7691`. 사용자 지시에 따라 최신 `origin/dev`의 모든 이력을 포함하는 신한 작업을 로컬 `dev`로 전진시켜 이어서 작업했다. 기존 작업 브랜치와 미추적 기획·UTM 문서는 보존했다.

최신 지시는 **연결 코드 준비까지**다. 새 로컬 API·DB를 구축하거나 실행하지 않는다. dev API의 확정 주소와 서버 준비 완료 안내를 받은 뒤 실제 연결·저장을 검증한다. 아래 이전 로컬 검증 기록을 dev 검증으로 해석하지 않는다.

## 범위와 환경

사용자가 운영 준비 상태 검사를 중단하고 기존 개인정보 전문을 사용하도록 지시했다. 별도 승인 확인을 작업 조건으로 요구하지 않고, **서버에 등록된 전문·버전을 조회해 그대로 표시·제출**한다. 이번 실제 검증은 `HOST_REGISTRATION`만 대상으로 하며 이전 단계의 다른 유형 구현은 보존한다.

## 지금 가능한 프론트 수정

- 기존 `/api/shinhan/*` BFF, 서버 전용 bridge·client HMAC, HttpOnly 세션 쿠키, Origin·CSRF·16KiB 제한, 경로/메서드 allowlist, Zod 응답 검증을 재사용한다.
- 방 등록의 주거형태·위치 오류를 해당 입력 항목 옆에도 표시한다. 전화번호·필수 동의 오류, pending·중복 클릭 차단, 서버 성공 후 완료, 접수 후 조회 전용은 기존 연결을 유지한다.

- 걱정 저장에서 동의 버전 오류가 난 뒤 전문 재준비가 503으로 실패하면 다시 준비할 버튼이 사라지는 문제를 고쳤다. 거절된 요청을 정리한 뒤 사용자가 전문 준비를 명시적으로 실행한다. 실패해도 버튼·기존 신청·단계·입력·걱정 선택은 유지된다.
- 서버 전문을 준비하기 시작한 뒤에는 전문 조회 실패를 Figma 예시 전문으로 대체하지 않는다. 개인정보 페이지에 준비 상태와 복귀·재준비 수단을 표시한다. 아직 서버 준비를 시작하지 않은 순수 화면 예시 흐름은 기존 예시 전문을 유지한다.
- 새 전문을 불러와도 동의는 자동 선택하지 않는다. 현재 전문과 기존 신청의 필수 동의 버전이 다르면 그 차이를 표시하고 기존 동의 기록을 변경하지 않는다.
- 서버 준비 중에는 후속 저장·이동 버튼을 잠가 중복 동작을 방지한다.
- 동의문 조회·신청 내역 조회·세션 준비·저장 오류의 안내를 구분했다. 조회 실패를 저장 실패라고 표시하지 않고 마지막으로 확인한 신청 내역을 유지한다. 원시 서버 오류 내용은 표시하지 않는다.
- HTTP 상태·오류 코드·재시도 가능 여부·`Retry-After`·멱등 키 처리와 기존 401/409/422 의미는 유지했다. 미확정 건너뛰기·미동의 진행 방식은 변경하지 않았다.

기존 FSD 구성과 UI를 활용했다. route·API 계약·의존성·빌드 캐시는 변경하지 않았다.

## 검증

### 앞선 로컬 API 검증

사용자가 연결 준비 단계로 범위를 변경하기 전에 수행한 PC 브라우저 검사 **30개 통과**, 실패·브라우저 예외·예상 밖 콘솔 오류 0건이다. 합성 신청 3건을 기존 로컬 DB에 저장했다. 근거는 기존 검증 폴더의 `stage11-host-registration-desktop-report.json`이다.

- 실제 API의 201 저장 성공 뒤에만 완료 표시, 422 필드 오류와 입력 보존, 제출 중 중복 클릭 차단, 접수 후 읽기 전용 내역을 확인했다.
- 서버 저장 후 브라우저 응답만 유실시킨 뒤 같은 키·본문으로 재시도해 같은 신청 ID와 멱등 재현을 확인했다.
- 서명된 쿠키의 만료 시각을 과거로 설정해 실제 BFF 401을 확인했다. 서버 DB를 수정하거나 실제 2시간 경과를 기다린 검증은 아니다.
- 이 작업이 소유한 API 프로세스만 중지해 실제 연결 장애 503과 거짓 완료 방지를 확인했다. 같은 API·DB 재시작 후 같은 키·본문의 재시도는 성공했다.
- 개인정보 전문 왕복 때 입력·진행 상태가 유지됐고 PC 1440px 가로 넘침이 없었다.
- 검증 도구가 시작한 API와 브라우저는 종료했고 Next 개발 서버도 중지했다. 고객 발송·운영 시트 쓰기는 실행하지 않았다.

이번 수정의 모바일 재검증과 실제 dev 검증은 **미실행**이다. 이전 10단계의 PC·모바일 검증과 구분한다. 준비했던 전체 예시 응답 브라우저 검사는 실행하지 않았다.

### 연결 준비 점검

인계 1.1.0 및 두 계약 1.0.0과 기존 BFF·익명 세션·동의 조회·호스트 방 등록 DTO를 대조했다. 확인된 불일치는 없으며 원격 환경의 미확정 정책을 구현하지 않았다. development·loopback·응답 환경 검사, Origin·CSRF, 본문 크기·관리자 경로 차단을 유지했다. 이번 준비 작업에서 API·DB·worker를 시작하거나 실제 저장 요청을 보내지 않았다.

정적 검사 최종 결과는 커밋 전 기록한다. 서버에 요청할 내용과 연결 재개 조건은 [dev API 연결 인계](./shinhan-dev-api-handoff.md)에 정리했다.

## 실행 방법과 환경변수

프론트 `.env.local`의 서버 전용 변수는 `SHINHAN_API_ORIGIN`(origin만, 로컬 `http://127.0.0.1:3200`), `SHINHAN_BRIDGE_SECRET`, `SHINHAN_CLIENT_IP_HMAC_SECRET`, `SHINHAN_ALLOWED_ORIGINS`(정확한 프론트 origin을 쉼표로 구분)이다. 비밀값을 `NEXT_PUBLIC_*`로 선언하지 않으며 `.env.local`은 커밋하지 않는다.

화면 개발 서버는 고객 저장소에서 `node node_modules/next/dist/bin/next dev --webpack --hostname 127.0.0.1 --port 3000`으로 실행한다. 기존 방 등록 개발 경로는 `http://127.0.0.1:3000/shinhan/dev/host/register`다. API가 없을 때는 준비 실패가 정상이며 예시 응답으로 실제 저장을 가장하지 않는다. 이번 준비 단계에서는 로컬 API·DB를 실행하지 않는다. dev 주소를 받더라도 미확정 환경·세션 계약을 먼저 적용·검증해야 하므로 현재 환경변수의 URL만 교체해서는 안 된다.

## 남은 작업

1. 다른 세 신청 유형은 다음 단계의 연결·검증 범위로 남긴다. 기존 구현을 삭제하거나 다시 작성하지 않는다.
2. 실제 dev API 주소·준비 완료 안내 및 원격 환경·세션 계약을 받은 뒤 호스트 방 등록부터 PC·모바일 연결 검증.
3. 외부 알림·시트 연결과 실제 전달 상태, 실제 모바일·Safari·신한 앱 웹뷰 검증.

사용자의 후속 지시로 신한 변경만 main에 반영·배포한다. dev 전체를 병합하지 않고 main 기반 작업 공간에서 신한 변경만 선별한다. 실제 접수의 development·loopback 가드는 유지하며 화면 배포를 dev API 통합 검증 완료로 보고하지 않는다. 기존 미추적 기획·UTM 문서는 포함하지 않는다.
