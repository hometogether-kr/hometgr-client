## 준비된 고객 코드

| 위치                                     | 역할                                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| `src/app/api/shinhan/[...path]/route.ts` | 얇은 동일 출처 BFF route                                                                 |
| `src/features/shinhan-bridge/`           | 서버 전용 키, HttpOnly 세션, Origin·CSRF·16KiB·경로/메서드 제한, Zod·계약 버전·환경 검증 |
| `src/domains/shinhan-application/`       | 동의·신청 읽기, 응답 DTO, 조회/저장 오류 안내 구분                                       |
| `src/features/shinhan-intake/`           | 동의 준비, 세션 생성, 초안 보존, 요청 DTO와 멱등 키, 실패·재시도                         |
| `src/widgets/shinhan-host-registration/` | OWNED/RENTED, 자유 위치, 전화번호·동의, 필드 오류, 실제 성공 후 완료                     |

세션 토큰은 응답 JSON·브라우저 저장소·URL·로그에 노출하지 않는다. 제출마다 행동 키를 만들고 결과가 불명확한 재시도는 같은 키·본문·세션을 유지한다. 서버 저장 성공과 알림 전달·시트 반영은 구분한다. 전문 조회 실패를 예시 전문으로 대체하지 않으며 개인정보 왕복과 오류에서 입력을 보존한다.

## 서버 담당에게 요청할 확정 정보

1. **접속과 준비 완료:** 확정된 dev HTTPS API origin, 고객 웹 origin, 배포 SHA, 공개 계약 버전 및 API·DB 준비 완료 안내. 관리자 도메인·EC2 IP·도메인 후보로 대체하지 않는다.
2. **환경 경계:** 고객 BFF의 배포 환경 선택 방식과 기대 `X-Shinhan-App-Env`, dev/운영 데이터 공유 시 세션·공개 bridge key의 범위. `NODE_ENV=production`인 dev 빌드의 정책을 명시해 달라.
3. **클라이언트 식별:** 실제 고객 호스팅에서 신뢰할 IP 헤더·프록시 체인, 위조 헤더 처리, IP 정규화 및 `X-Shinhan-Client-Key` HMAC 입력·키 범위. 브라우저 전달 헤더를 그대로 신뢰하지 않는다.
4. **익명 세션 초기화:** 여러 BFF 인스턴스·탭의 동시 초기화와 응답 유실 시 같은 세션 복구/중복 방지 계약. 현재 프로세스 메모리 Map은 원격 분산 환경의 해결책이 아니다. 새 세션 발급을 자동 재접수 수단으로 사용하지 않는다.
5. **HTTPS 쿠키:** 세션/CSRF 쿠키 이름·속성·만료·초기화/회수 정책. 현행 `shinhan_intake` 및 `shinhan_csrf`와의 전환 방식. `__Host-` 권장안을 확정 계약처럼 적용하지 않는다.
6. **기존 동의 전문:** 사용자가 지정한 기존 전문이 dev에 등록된 버전·본문·해시 및 `localOnly=false` 조회 준비 여부. 별도 승인 증빙 검사를 다시 요구하는 항목이 아니다. 조회한 버전 그대로 제출한다.
7. **합성 저장 범위:** dev·운영 데이터 공유 환경에서 사용할 합성 데이터 구분과 테스트 범위, 외부 발송·운영 시트 쓰기 비활성 상태. worker의 작업 처리 여부도 안내해 달라.

현재 고객 DTO에 필요한 변경은 발견하지 못했다. 위 원격 정책은 서버 담당 계약 확정 전까지 구현하지 않는다.

2026-10-24 사용자 지시에 따라 서버 대화창 **신한 서버·DB 기반 구현 시작** (`01a161a5-540d-78f0-ac2a-75ab111d2212`)에 위 요청을 전달했고, 서버 담당의 접수 및 검토 시작을 확인했다. 정책·계약 문서 갱신과 준비 완료 정보 요청이며, 새 자원 생성·DB 초기화·운영 배포·외부 쓰기를 승인한 요청은 아니다. 비밀값은 포함하지 않았다. 갱신된 계약 수신 전까지 원격 연결은 보류한다.

`runtime-split-contract-v1.md`의 이전 dev/운영 DB 분리 문구가 최신 공유 DB 결정과 달라 서버 담당에게 정정을 추가 요청했다. 고객 코드는 최신 사용자 결정과 인계 1.2.1을 우선하며 세션·키·worker 정책까지 공유한다고 추정하지 않는다.

## 연결 재개 순서

1. 확정 URL·준비 완료·원격 경계 계약 수신 후 기존 가드와 동등한 검증을 갖춰 명시적인 dev 환경을 추가한다. 단순 가드 삭제나 URL 치환은 하지 않는다.
2. 고객 서버 환경에 `SHINHAN_API_ORIGIN`, `SHINHAN_BRIDGE_SECRET`, `SHINHAN_CLIENT_IP_HMAC_SECRET`, `SHINHAN_ALLOWED_ORIGINS`를 설정한다. 값은 비밀 저장소로 전달하며 `NEXT_PUBLIC_*`, Git·채팅에 넣지 않는다. 새 환경 변수는 계약 확정 후 문서화한다.
3. 먼저 동의 조회·익명 세션·쿠키 및 토큰 비노출을 확인한다. 그 뒤 HOST_REGISTRATION의 실제 201·422·동일 키 재요청·401·장애 시 거짓 성공 방지를 합성 데이터로 확인한다.
4. PC·모바일에서 제출 중 중복 클릭 차단, 개인정보 왕복 값 유지, 접수 후 조회 전용 내역을 검증한다. 실제 API 결과와 오류 주입 결과를 구분해 기록한다.
5. 이 결과를 보고한 뒤 다른 세 유형을 진행한다. 기존 신한 화면·연결 준비 코드는 앞선 사용자 지시로 `main`의 `6067ffe`까지 선별 배포됐다. 이번 작업은 `dev`에서 수행하며 새 main 반영·배포를 실행하지 않는다. 실제 접수의 기존 보안 가드는 유지한다. 실제 고객 발송·운영 시트 쓰기는 별도 지시 대상이다.

기존 로컬 API 검증은 `shinhan-frontend-stage-10.md` 및 `shinhan-frontend-stage-11.md`에 기록되어 있으며 원격 dev 검증 근거로 사용하지 않는다.
