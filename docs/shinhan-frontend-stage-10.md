## 구현

- 네 신청 입력을 각각 계약 DTO로 검증·변환해 실제 저장한다. 호스트 견적은 기존 카카오 주소검색, 날짜는 기존 Calendar, 나머지 위치는 자유 입력을 유지했다.
- 같은 출처의 `/api/shinhan/*`가 허용된 고객 API만 중계한다. bridge secret과 익명 토큰은 브라우저 JSON에 전달하지 않으며 토큰은 서명된 HttpOnly 쿠키에 둔다. 정확한 Origin·Host·CSRF, 제한된 JSON 크기, 응답 계약 버전·환경·Zod, timeout을 검증한다.
- 서버의 동의 전문과 익명 세션을 명시적으로 준비한 뒤 필수 동의를 다시 받는다. 동의 전문의 내용 해시도 BFF에서 확인한다. 여러 탭의 초기 준비는 Web Locks와 서버 초기화 재사용으로 직렬화한다.
- API 성공 상태와 응답 검증을 모두 통과한 이후에만 `/shinhan/dev/application`의 결과·완료 화면으로 이동한다. 개발 예시 화면은 별도 경로·버튼으로 유지하며 실제 저장 실패의 대체 응답으로 사용하지 않는다.
- 호스트 예상 금액은 저장 응답의 계산 스냅샷을 그대로 표시한다. 조건 수정 후 달라진 내용은 새 요청 키로 새 견적을 저장하며 이전 견적은 변경하지 않는다. 같은 입력의 결과 다시 보기는 새로 저장하지 않는다.
- 방 등록과 게스트 두 신청은 저장 후 입력을 조회만 할 수 있다. 공통 사진·신청 내역·가이드 재열람은 읽기 동작이다. 서버 `current` GET으로 현재 상태를 다시 확인할 수 있다.
- 걱정 선택과 명시적인 선택 동의는 별도 PUT으로 저장한다. 동의한 빈 응답과 미응답을 구분한다. 전체 가이드 열람은 `SKIPPED`나 추가 저장을 전송하지 않는다.
- 호스트 소개서는 별도 POST 성공 뒤 완료 화면으로 이동한다. 접수와 알림 전달을 구분하며 `PENDING`을 전달 완료로 표시하지 않는다. 미확정 건너뛰기·미동의 진행·걱정 저장 실패 후 진행은 추가하지 않았다.
- 최초 제출의 내용과 UUID 요청 키를 보관해 네트워크 오류·503·429·응답 형식 오류에서 동일 요청으로 재시도한다. pending 동안 중복 제출과 입력 수정을 잠근다. 429는 `Retry-After`가 지나야 재시도할 수 있다. 세션 만료와 멱등 충돌에서 세션 생성·재접수를 자동 실행하지 않는다.
- 실패해도 초안과 이미 저장한 기본 신청은 유지한다. 조회와 저장이 겹칠 때 이전 GET이 새 저장 결과를 덮어쓰지 않도록 기존 조회를 취소한다. 미확정 요청이 있으면 새로고침·탭 닫기를 경고한다.
- 공유 intake layout의 초안·후속 단계·선택값·동의 스냅샷·요청 시도 상태는 개인정보 전문 왕복에도 유지한다. 신청 정보·익명 토큰을 URL이나 localStorage/sessionStorage에 기록하지 않는다. 새로고침 후 신청 내역 복원은 이번 계약·범위에 없으며 가드를 표시한다.

## 구조와 화면 기준

route는 개발 모드 제한과 page composition만 담당한다. `pages-layer`가 기존 호스트 결과/소개서 프레임·게스트 가이드·공통 사진과 새 완료 프레임을 Server 슬롯으로 조합한다. 입력·저장 흐름과 상태는 feature, 응답 모델·조회·검증은 domain, 중계는 server-only feature로 분리했다. 익명 신청 query cache는 일반 회원 로그인 401 처리와 분리해 작성 중 신청을 보존한다.

Figma 구현 스킬로 호스트 소개서 완료 `327:4186`, 방 등록 심사 `475:1026`, 게스트 예산 완료 `575:1661`, 게스트 수요 접수 `512:1708`의 high-fidelity context와 스크린샷을 확인했다. 기존 캐릭터·브랜드·공통 사진을 재사용했다. 모바일은 확정된 기획의 단일 열·좌우 20px·28~32px 제목·16px 본문·최소 48px 버튼 기준이다. 실제 저장 여부·로컬 동의·외부 발송 비활성 안내와 조회 전용 요약이 시안에 추가됐다.

실제 저장은 로컬 검증 DB에 합성 정보로 수행했다. 브라우저 오류 주입은 서버 코드·설정을 변경하지 않았으며 API·BFF의 Origin/CSRF 검사를 완화하지 않았다. 브라우저 런타임 예외는 없었고, 실패 시나리오의 예상 네트워크 오류는 콘솔에 남는다. 기존 이미지 일부의 Next 크기 경고는 관찰했으며 확인한 캡처에서 비율 깨짐은 없었다.

중간 실패를 제외하지 않고 다음처럼 기록한다.

- 첫 PC 응답 유실 재현 도구는 `route.fetch()`의 Host/Fetch-Site 헤더 누락으로 BFF 403을 받았다. 도구에 실제 브라우저 헤더를 전달하도록 수정했고, 실제 201 이후 응답 유실·동일 신청 재시도는 별도 실행에서 통과했다.
- PC 중간 실행에서 저장 성공 이후 현재 내역 GET이 실제 503을 한 번 반환했다. 최종 재시도 구간 실행은 조회까지 모두 통과했다. 원인은 확정하지 않았다.
- 모바일 중간 실행에서 호스트 동의 전문 GET이 실제 503을 반환해 준비 대기를 중단했다. 통과한 방 등록·게스트 검증은 보존하고 호스트·공통 실패 구간만 다시 실행해 모두 통과했다. 원인은 확정하지 않았다.
- 최종 증거는 PC 주 흐름 59개와 재시도 13개, 모바일 앞선 주 흐름 51개와 호스트·재시도 35개의 성공 검사다. 도구 오류로 얻은 PC 1개 검사와 중단 전 모바일 카카오 선택 중복 1개는 합산하지 않았다. 중간 보고서의 실패 상태를 성공으로 덮어쓰지 않았다.
