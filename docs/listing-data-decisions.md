# 매물 등록·입주자 메인 데이터 기준

2026-10-01 사용자 결정. 상세 페이지 addressRegion 누락 오류 수정은 보류한다. 백엔드는 이번 확인에서 변경하지 않았다.

## 확정한 방향

- 매물 유형: 등록자 관점의 아파트·오피스텔·단독주택·쉐어하우스 4종을 등록·탐색·상세에서 통일한다. 오피스텔과 쉐어하우스를 같은 값으로 취급하지 않는다.
- 이용 인원: 현재 거주 인원과 새로 입주할 수 있는 인원의 두 항목으로 구분하여 저장·표시한다. 기존 residentCount와 roomCapacity의 의미·저장값을 대조하여 재사용한다. 탐색의 입주 가능 인원 조건은 후자를 사용한다.
- 전용면적: 게스트 방이 아닌 집 전체의 전용면적이다. 기존 areaRange를 재사용하여 상세정보에 '20평대' 같은 범위를 표시한다. 정확한 ㎡ 입력·저장 추가는 이번 범위에서 제외한다.
- 제목: 시군구+읍면동+의+유형으로 자동 생성. 예: 노원구 공릉동의 아파트. 소제목: 관리자가 작성하는 교통·거리 등의 한 줄 설명. 관리자 페이지에서 매물을 검수하면서 작성하는 구조로 한다. 소제목 전용 필드와 관리자 매물 편집 UI를 추가하기로 확정했다. 실제 구현은 아직 적용하지 않았다.
- 층수 제안(미확정): 일반적인 숫자 호수는 302호→3층, 1602호→16층으로 자동 추정하여 등록자에게 확인·수정 가능하게 제시한다. 호수만으로 모든 건물의 층을 보장할 수는 없으므로 확정값으로 간주하지 않는다. 비표준 형식은 추정하지 않고 입력받는다.
- 지하층 호수 예시(사용자 추가): B101호는 지하 1층으로 자동 추정하는 사례에 포함한다. 추정 결과는 등록자가 확인·수정할 수 있도록 한다.
- 비회원: 제목과 동 단위 지역 공개. 상세 주소·상세 계약정보·위치 안내·집주인 정보 비공개. 사진·목록 가격 등 나머지 필드의 범위는 별도 확인 필요.
- 회원: 층수·도로명 주소·위치는 공개하되 건물 동·호수는 비공개다. 일반 회원용 서버 응답에서 addressDetail을 제외한다. 소유자·권한 있는 관리자의 업무용 조회는 구분한다.
- 집주인 인증: 추후 도입한다.
- 앞으로 공개하는 실제 매물에는 주소와 가격이 있어야 한다. 기존 예시 데이터는 실제 운영 매물 기준으로 삼지 않는다. 작성 중 임시저장의 누락과 최종 제출·게시의 누락은 구분한다.

## 다음 순서

구체적인 요청·응답 변경안은 [API 변경 명세 초안](listing-api-change-spec.md)에 정리했다. 확정 기준과 미확정 설계안을 구분하며, 실제 API는 아직 변경하지 않았다.

1. 위 기준으로 API 변경 명세 확정: 유형, 구조화된 지역, 두 인원 항목, 기존 면적 범위 재사용, 소제목, 회원별 공개 범위, 최종 제출 필수값. 층수 자동 추정·확인 정책은 별도 확정.
2. 등록 UI·저장 API·관리자 소제목 편집을 맞춘 뒤 소수 실매물 시험 등록.
3. 동일 매물의 메인 카드·탐색·상세 데이터와 검색 조건 연결. 상세 오류 수정 보류는 유지.
4. 실제 데이터로 반응형·Figma·전체 흐름 검증 후 전체 이관.

## 최신 주석 반영 기록 (2026-10-01)

- 현재 거주 0명 허용. 0명일 때 구성·성별은 해당 없음으로 처리한다.
- 관리자 주소 조회 후 면적 보완은 검토안으로 남긴다. 기존 평수 범위 사용은 유지한다.
- 자유 검색 대상 및 학교·역 연관 방식은 추후 결정한다.
- 관리자 주소 숨김 UI는 이번 범위에서 제외하고 기존 API는 보존한다.
- 실매물 시험은 2~3개. 주소·가격 누락 시험은 제외하되 필수 입력 정책은 유지한다.
- 등록 설명 입력에 학생에게 보여지는 내용이라는 안내와 자세한 예시를 추가한다. 예시는 placeholder/도움말이며 실제 저장값으로 자동 입력하지 않는다.
- [백엔드 전달사항](listing-backend-handoff.md), [프런트 작업 목록](listing-frontend-work-items.md)에 구현 분담을 기록했다. 아직 전달·구현 완료를 의미하지 않는다.
