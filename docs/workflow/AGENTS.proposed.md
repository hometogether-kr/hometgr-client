# AGENTS.md 추가·개정안

검토용 초안. 이 문서는 현재 루트 AGENTS.md를 대체하지 않는다. 채택 시 아래 내용을 기존 개발 지침에 추가하고, 기존 Testing And Verification 절은 아래 검증·테스트 절로 교체한다. Next.js·FSD·Zod·서버/클라이언트·접근성 등 기존 상세 규칙은 유지한다.

## 개발 환경과 디스크 관리

- 기존 개발도구·의존성·빌드 캐시를 재사용한다. 단계·채팅·브랜치 변경만으로 삭제하거나 재설치하지 않는다.
- 개발 드라이브의 여유 공간이 5GB 미만이면 사용량을 조사한다.
- 정리 전 대상·예상 확보 용량·재생성 시간·다운로드 필요 여부를 제시한다. 활성 프로젝트 환경·공용 캐시 삭제는 사용자 확인을 받는다.
- 곧 다시 사용할 항목은 유지하고 다른 정리 후보를 찾는다.

## 작업 시작과 범위

- 관련 기능 명세·API 계약·기존 결정·작업 중 변경을 먼저 확인한다. 작업 흐름은 `docs/workflow/README.md`를 참고한다.
- 작은 문구·스타일 수정에는 새 명세를 강제하지 않는다. 사용자 행동·권한·데이터 계약을 바꾸는 작업은 관련 명세의 정책과 수용 기준을 먼저 정리한다.
- 확인된 사실·제안·미결정을 구분한다. 사용자 결과가 달라지는 미결정 정책은 추측하지 말고 질문한다. 답과 무관한 조사는 계속한다.
- 승인된 범위의 가역적인 구현과 기술적 세부사항은 재승인 없이 진행한다.
- 요청을 완수하는 데 필요한 연관 수정은 이유·영향을 설명하고 수행한다. 별도 기능·광범위 리팩터링은 구현하지 않고 끝에 제안한다.
- 기존 사용자 변경을 덮어쓰거나 되돌리지 않는다. 배포·데이터 변경·외부 작업은 기존 권한과 요청 범위를 확인한다.

## 결정 기록

- 데이터 모델·조회 전략·레포 분리·상태 보관 위치 등 되돌리기 비싼 선택에는 구현 전 ADR 초안을 작성한다. 일상적인 코드 선택에는 강제하지 않는다.
- 구현 전 `docs/decisions/README.md`와 관련 기존 결정을 읽는다. 인덱스가 없으면 없음을 밝히고 기존 관련 문서를 조사한다. 문서 부재를 새 결정의 근거로 삼지 않는다.
- 기존 승인 결정과 충돌하면 영향받는 구현을 멈추고 대안·영향을 알린다. 새 선택이 확정되면 ADR을 승인 상태로 기록하고 구현한다.
- 제품 정책은 기능 명세, API 형식은 계약, 기술 선택은 ADR, 이번 변경은 PR/완료 보고에 남긴다. 같은 사실을 여러 문서에 복제하지 말고 링크한다.

## 검증

- 코드 변경의 완료 전 `pnpm lint`, `pnpm format:check`, `pnpm exec tsc --noEmit`, `pnpm build`와 관련 테스트를 실행한다. UI 변경은 dev 서버와 브라우저로 관련 흐름·반응형·오류 상태를 확인한다.
- 필수 검사 실패·미실행 상태를 구현 완료로 보고하지 않는다. 이번 변경·기존 오류·환경 문제를 구분하고 실제 로그와 미검증 범위를 보고한다. 실패 원인을 추측해 단정하지 않는다.
- 문서·스킬만 바꾼 작업은 변경 파일 포맷·링크·스킬 구조를 확인한다. 제품 빌드나 UI 검증은 강제하지 않으며 생략 이유를 밝힌다.
- 검사 도구가 없거나 환경이 부족하면 먼저 기존 도구를 확인한다. 검사를 통과한 것처럼 표현하거나 불필요한 설치·캐시 삭제로 우회하지 않는다.

## 테스트

- 테스트 케이스는 확정 요구사항·API 계약을 기준으로 Codex가 정상·경계·실패 상황을 제안한다. PM은 제품 정책에 해당하는 불명확한 기대 결과를 확정한다. 명확한 케이스는 매번 승인받지 않는다.
- 매퍼·URL 파싱/직렬화·포맷 유틸·Zod 스키마 변경은 의미 있는 자동 테스트로 검증한다. 구현을 복제하는 테스트나 통과만 확인하는 단언을 피한다.
- 테스트 환경이 없으면 최소 도입 범위와 검증 방법을 먼저 제안한다. 별도 인프라 설치를 임의로 확대하지 않는다. 필요한 자동 검증을 못 했다면 병합 준비 완료로 보고하지 않는다.
- 컴포넌트 렌더 테스트는 요청 없이 만들지 않는다. 테스트 통과가 사용자 경험·전체 서비스 정확성을 보증한다고 표현하지 않는다.

## 설명과 완료 보고

- 기능 단위 보고에서 무엇을 바꿨는지 / 왜 택했는지 / 깨지면 어느 화면이 어떻게 보이는지를 짧게 설명한다.
- 관련 파일 링크·실제 검증 결과·미검증 사항·남은 위험을 함께 적는다. 전체 파일 내용은 요청 시 제공한다.
- 필요한 낯선 용어만 비전공자 기준 한 줄로 설명한다. 고정 개수를 채우기 위해 설명을 추가하지 않는다.
- 코드·문서·실행으로 확인하지 못한 사실은 `확인 안 됨`이라고 쓴다. 가능성 있는 위험은 확인된 영향과 구분한다.

## FSD 적용 확인

- 의존 방향은 app → pages-layer → widgets → features → domains → shared다.
- 서로 다른 같은 레이어 slice의 직접 의존을 피하고 상위 레이어에서 조립한다. 같은 slice 내부는 상대 경로, 다른 slice는 index.ts 공개 API를 사용한다.
- 상세 책임과 예외 판단은 기존 FSD 지침을 따른다. 작업 흐름 문서가 아키텍처 규칙을 덮어쓰지 않는다.

## 피드백 루프

- 같은 지적이 두 번 나오면 일회성 요구인지 반복 가능한 원칙인지 판단해 규칙 추가를 제안한다. 규칙을 자동 추가하지 않는다.
- 규칙이 중복되거나 반복해서 불필요한 정지를 만들면 통합·수정을 제안한다.
