# 홈투게더 작업 흐름 초안

상태: 검토용 초안 / 작성일: 2026-10-15

목표는 수정 자체를 없애는 것이 아니라, 정책 누락과 서로 다른 가정 때문에 생기는 재작업을 줄이는 것이다. 사용하면서 새로 발견한 문제는 정상적인 학습으로 취급한다.

## 시작 방법

1. 사용자 목적 하나를 고른다. 예: 방을 찾고 상세 정보를 확인한다, 호스트가 매물을 등록한다.
2. [기능 명세 템플릿](feature-spec.template.md)을 복사해 `docs/features/<기능명>.md`에 작성한다. 처음에는 목적·범위·미결정 사항만 채워도 된다.
3. 아래 순서로 빈칸을 좁힌 뒤 작은 단위로 구현한다. 모든 작업에 새 승인을 받을 필요는 없다. 이미 확정한 범위의 가역적인 구현은 Codex가 진행한다.
4. [AGENTS 개정안](AGENTS.proposed.md)은 기존 개발 지침에 추가하는 검토용 문서다. 루트 AGENTS.md를 아직 바꾸지 않았다. 스킬 초안도 `skill-drafts/`에 있어 자동 적용되지 않는다.

## 단계별 역할과 통과 조건

| 단계            | PM이 결정할 것                                                       | Codex가 맡을 것                                                       | 남기는 결과 / 다음 단계 조건                                     |
| --------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 1. 목적과 범위  | 대상 사용자, 해결할 문제, 이번에 제공할 행동, 제외 범위              | 기존 화면·문서·코드 조사, 중복 구현과 미확인 사실 표시                | 목적 한 문장과 사용자 관점 완료 조건                             |
| 2. 정책과 예외  | 권한, 입력 제한, 공개 조건, 실패·이탈 시 기대 행동                   | 정상·경계·실패 상황 제안, 선택지와 영향 비교                          | 구현 결과를 바꿀 정책에 답이 있거나 이번 범위에서 제외됨         |
| 3. 화면 흐름    | 정보 우선순위, 문구, 이동 흐름, 모바일에서의 사용성                  | 와이어프레임·프로토타입 제안, 로딩·빈 결과·오류·완료·키보드 상태 점검 | 상태별 화면과 수용 기준 연결. 불확실한 사용성은 먼저 작게 검증   |
| 4. 데이터와 API | 사업상 의미가 있는 상태·권한·보존 정책, 비싼 선택의 제약과 허용 비용 | 실제 계약 조사, 요청·응답·오류·상태 전이 제안, FSD 배치와 ADR 초안    | 프론트와 백엔드가 같은 필드·상태·오류를 사용. 미구현 API는 명시  |
| 5. 작은 구현    | 우선 구현할 사용자 흐름, 범위 변경 여부                              | 화면→요청→응답→결과 표시 연결, 필요한 코드와 테스트 작성              | 동작 가능한 최소 흐름. 모의 데이터 단계면 실연동 완료와 구분     |
| 6. 검증과 리뷰  | 수용 기준 충족 여부, 사용자 경험의 수용 여부                         | 검사·테스트·브라우저 확인, 실패 분류, explain-diff                    | 수행 결과와 미검증 범위가 남음. 필수 검사 실패 시 구현 완료 아님 |
| 7. 배포와 학습  | 배포 시점·대상, 관찰할 문제와 성공 기준                              | 배포 영향·되돌리기 검토, 승인된 배포 수행, 발견 사항 정리             | 배포 권한 확인. 사용자 확인·오류·다음 개선 사항을 기록           |

PM이 결정하는 것은 제품의 행동과 우선순위다. Codex는 구현 방법과 검증 방법을 제안하고, 승인된 범위의 기술적 세부사항을 처리한다. 권한·데이터 손실·과금·핵심 사용자 흐름을 바꾸는 미결정 정책은 추측하지 않는다. 그 답을 기다리는 동안 독립적인 조사와 문서 작업은 계속한다.

## 작업 규모에 맞춰 줄이기

- 문구·간격 등 작은 수정: 요청과 기대 결과 → 수정 → 관련 확인. 새 기능 명세나 ADR 불필요.
- 기존 기능의 행동 변경: 기존 명세의 해당 정책·수용 기준을 갱신한 뒤 구현.
- 새 사용자 흐름 또는 여러 레포에 걸친 변경: 전체 순서를 사용하되 기능 하나씩 연결한다.
- 사용성이나 기술 가능성이 불확실한 기능: 제한된 프로토타입부터 만든다. 프로토타입에서 확인한 사실만 정식 명세에 반영한다.

## 기록의 기준

| 기록              | 관리하는 사실                                | 갱신 시점                                     |
| ----------------- | -------------------------------------------- | --------------------------------------------- |
| 기능 명세         | 사용자 행동, 제품 정책, 화면 상태, 수용 기준 | 정책·범위 변경 시                             |
| API 계약          | 요청·응답·오류·권한과 필드 의미              | 계약 변경 전후                                |
| ADR               | 되돌리기 비싼 기술 선택과 근거               | 구현 전 초안, 확정 후 승인, 전제 변경 시 대체 |
| PR 또는 완료 보고 | 이번 변경, 검증 결과, 남은 위험              | 구현 단위 완료 시                             |

기존 매물 관련 자료는 [API 계약](../listing-contract-stage-1.md), [데이터 결정](../listing-data-decisions.md), [API 변경 명세](../listing-api-change-spec.md), [백엔드 전달](../listing-backend-handoff.md), [프론트 작업 목록](../listing-frontend-work-items.md)을 먼저 조사한다. 이 링크는 현재 구현과의 일치를 보증하지 않는다. 충돌하면 문서 날짜만으로 우선순위를 정하지 말고 코드·계약·결정자의 확인을 함께 기록한다. 과거 문서를 모두 소급 ADR로 바꾸지는 않는다.

프론트·API·어드민·인프라를 함께 바꿀 때는 기능 명세 하나에서 각 레포 작업과 계약을 연결한다. 프론트 저장소의 지침이 다른 레포에 자동 적용된다고 가정하지 않는다.

## 변경이 생기면

Codex가 변경 이유, 영향받는 수용 기준·화면·API·데이터, 필요한 재검증을 짧게 제시한다. PM은 지금 반영 / 다음 작업 / 제외를 결정한다. 합의된 범위 안의 수정은 재승인 없이 진행한다. 큰 계약이나 기존 ADR과 충돌하는 변경은 해당 부분을 멈추고 결정을 받는다. 합의한 문서를 먼저 갱신해 화면·백엔드·프론트가 다른 가정으로 작업하지 않게 한다.

## 바로 사용할 요청문

### 기획 시작

> [사용자]가 [목적]을 완료하는 기능을 만들자. 우선 구현하지 말고 기존 문서와 코드를 확인해 기능 명세 초안을 작성해줘. 확인한 사실·제안·미결정을 구분하고, 답에 따라 화면/API가 달라지는 질문부터 묶어줘. 선택지와 추천 이유도 적어줘.

### 구현 시작

> [명세 경로]의 확정 범위를 구현해줘. 관련 결정과 계약을 읽고 영향 파일·테스트 케이스·미결정 정책을 먼저 확인해줘. 정책이 명확하면 기술적 세부사항은 맡아서 진행하고, 제품 행동이 달라지는 미결정 사항만 질문해줘. 기존 변경은 보존해줘.

### 완료 검토

> 이번 작업 변경만 설명해줘. 비교 기준은 [base 또는 커밋]이고 내 기존 변경과 섞이지 않게 범위를 밝혀줘. 수용 기준별 근거, 실제 실행한 검사, 브라우저 확인, 미검증 사항, 문제가 나면 사용자에게 어떻게 보일지와 되돌리기 방법을 정리해줘.

## 첫 적용의 크기

다음 기능 하나에서만 이 흐름을 사용한다. 완료 후 정책 누락으로 되돌아간 횟수, 구현을 막은 미결정 사항, 문서와 실제 동작의 차이를 돌아본다. 기록이 많아 검토가 느려졌다면 중복 항목을 줄인다. 같은 지적이 반복되면 일회성 요구인지 공통 원칙인지 확인한 뒤 규칙 추가를 제안한다.
