# 매물 등록·탐색·입주자 메인 API 변경 명세 초안

작성일: 2026-10-01. 상태: 검토용 제안이며 구현·배포되지 않았다.

근거: [사용자 결정](listing-data-decisions.md), 백엔드 `docs/API-SPEC.md`, 등록 DTO·관리자 DTO, 프런트 등록 스키마·매물 조회 코드. 아래 경로는 BFF가 아닌 백엔드 기준이다.

최신 전달 기준: [백엔드 전달사항](listing-backend-handoff.md). 2026-10-01 주석을 반영했으며 이전 제안 중 검색·관리자 주소 숨김 UI는 이번 구현에서 제외했다.

## 1. 범위와 결정 상태

확정된 제품 기준:

- 유형은 아파트·오피스텔·단독주택·쉐어하우스. 등록·목록·상세에서 같은 의미로 사용한다.
- 현재 거주 인원과 새로 입주 가능한 인원을 구분한다.
- 집 전체 전용면적은 기존 평수 범위로 표시한다. 정확한 ㎡ 입력은 추가하지 않는다.
- 제목은 지역+유형 자동 생성, 소제목은 관리자 검수 화면에서 작성한다.
- 비회원에게 동까지의 지역을 공개하고 상세 주소·상세 계약정보·위치 안내·집주인 정보를 숨긴다. 회원에게는 층수와 도로명 주소·위치 안내를 공개하되 건물 동·호수는 공개하지 않는다. 소유자·권한 있는 관리자용 응답과 일반 회원용 응답을 구분한다.
- 새 운영 매물의 제출·게시에는 정확 주소와 가격이 필요하다.

이 문서에서 제안하는 필드명·길이·검색 방식은 API 설계안이다. 아직 미확정인 공개 필드 범위·층수 정책 등은 10절에 모았다. `addressRegion` 누락 오류 수정, 집주인 인증, 전체 노션 이관, S2 지역 요청 API는 이번 명세의 구현 범위에서 제외한다.

## 2. 변경 대상 API

| API                                           | 변경                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------- |
| `PUT /host/rooms/drafts/:draftId`             | step 3 유형·구조화된 지역 확장. 기존 step 4 인원·면적, step 7 입주 인원 유지 |
| `PATCH /host/rooms/drafts/:draftId/autosave`  | 새 필드 allowlist·검증 추가. 미완성 입력 임시저장 유지                       |
| `GET /host/rooms/drafts/:draftId`             | canonical data 및 autosaves에 새 필드 반환                                   |
| `POST /host/rooms/drafts/:draftId/submit`     | 정확 주소·지역·새 유형·가격 검증 강화                                        |
| `GET /host/rooms/:id`, `GET /admin/rooms/:id` | 새 지역·소제목 및 기존 인원·면적 반환                                        |
| `PATCH /admin/rooms/:id/subtitle` (신규 제안) | 관리자 소제목 단독 수정                                                      |
| `POST /admin/rooms/:id/approvals`             | 게시 직전 필수 데이터 재검증                                                 |
| `GET /rooms`                                  | 신규 필터 및 카드 데이터 추가                                                |
| `GET /rooms/:id`                              | 동일 데이터 기준·새 공개 정책 적용                                           |

기존 draft 낙관적 잠금 `expectedVersion`, 순차 완료, 소유권 검사, 성공 시 version 증가, stale version의 409 처리는 유지한다. 서버와 클라이언트 모두 새 필드 allowlist를 함께 변경한다.

## 3. 등록 필드 계약

### 3.1 유형 — step 3 `buildingType`

| 값(제안)        | 표시       |
| --------------- | ---------- |
| `apartment`     | 아파트     |
| `officetel`     | 오피스텔   |
| `detachedHouse` | 단독주택   |
| `shareHouse`    | 쉐어하우스 |

별도 중복 필드를 만들지 않고 기존 buildingType을 제품의 매물 분류로 사용한다. 법적 건축물 용도를 나타내는 필드로 해석하지 않는다. 새 등록에서 villa/other 및 buildingTypeOther 선택은 제거하되 기존 데이터 조회 호환은 유지한다. 기존 villa/other를 자동으로 detachedHouse/shareHouse로 바꾸지 않는다. propertyType/roomType 같은 legacy 필드로 새 값을 역추정하지 않는다.

### 3.2 주소·지역 — step 3 `region` 추가 제안

기존 addressRoad/addressDetail을 유지하고, 검색·제목용 region을 추가한다.

```json
{
  "step": 3,
  "expectedVersion": 7,
  "data": {
    "buildingType": "apartment",
    "addressRoad": "서울특별시 노원구 예시로 123",
    "addressDetail": "101동 302호",
    "addressRegion": "서울특별시 노원구 공릉동",
    "region": {
      "sidoName": "서울특별시",
      "sigunguName": "노원구",
      "eupMyeonDongName": "공릉동",
      "legalDongCode": "1135010300"
    }
  }
}
```

예시는 설명용 가상 매물이다. 코드·명칭은 실제 주소 공급자 및 기준 지역 데이터와 검증해야 한다.

- region은 법정동 기준으로 통일한다. 행정동과 혼용하지 않는다. 명칭은 trim 후 1~100자 제안.
- legalDongCode는 선행 0을 보존하는 10자리 문자열 제안. 정규식만으로 유효한 지역이라고 간주하지 않고 서버 기준 데이터와 계층·명칭을 검증한다.
- 시/군/구는 모든 지역에 각각 존재하지 않는다. sigunguName은 복합 명칭을 보존하며 해당 단계가 없는 지역은 null 허용. 읍·면·동과 리의 구분 및 공급자 매핑은 구현 전에 확정한다.
- 현재 주소 검색 결과의 sido/sigungu/bname을 합쳐 버리지 않고 보존한다. 코드 획득을 위한 SDK 결과 스키마 확장이 필요하다.
- addressRegion은 호환용 표시 문자열로 서버에서 region을 조합한다. 이행 기간에 요청으로 받으면 region과 불일치 시 400. 장기적으로 클라이언트 입력 중복을 제거한다.
- 도로명·상세 주소는 기존 trim 1~255자를 유지한다. region 코드가 있다고 실제 도로명 주소와 일치한다고 가정하지 않는다. 서버 검증 또는 관리자 검수로 일치 여부를 확인한다.
- autosave는 누락 입력을 허용한다. 완료 PUT은 기존 조건을 유지할 수 있으나, 새 기준 적용 이후 submit/approval은 approximateLocation만 있는 매물을 거부한다.
- 공개 제목은 `시군구 읍면동의 유형`: `노원구 공릉동의 아파트`. 시군구가 없으면 시도 사용. 상세 주소·동호수·건물명은 제목에 포함하지 않는다. 생성 규칙은 서버 한 곳에서 관리한다.

### 3.3 인원 — 기존 필드 유지

| 위치               | 필드            | 의미·검증                                                          |
| ------------------ | --------------- | ------------------------------------------------------------------ |
| step 4 household   | `residentCount` | 현재 거주 인원. 정수 0~100. 0명이면 구성·성별은 해당 없음          |
| step 7 preferences | `roomCapacity`  | 새로 받을 수 있는 인원 구간. 기존 `one`, `two`, `threeOrMore` 유지 |

roomCapacity는 예약에 따라 실시간 차감되는 재고 수량이 아니다. threeOrMore를 정확히 3명으로 변환하지 않는다. 기존 데이터가 다른 의미로 입력되었는지는 시험 매물 검수에서 확인한다.

### 3.4 면적 — 기존 step 4 `areaRange` 유지

`upTo10Pyeong`, `teensPyeong`, `twentiesPyeong`, `thirtiesPyeong`, `fortiesPyeong`, `fiftiesPyeong`, `overFiftyPyeong`, `unknown`을 그대로 반환한다. 상세에서 기존 레이블을 사용하고 unknown은 '면적 확인 필요'로 표시하는 안을 제안한다. privateRoomSize는 게스트 방 크기이며 집 전체 전용면적과 구분한다.

기존 레이블의 '50평대'와 '그 이상' 경계는 별도 검토 대상으로 남긴다. 이번 변경에서 임의의 숫자 범위로 재정의하지 않는다. areaSquareMeters로 환산하거나 새 ㎡ 입력을 요구하지 않는다.

관리자가 주소로 면적을 확인해 보완하는 방안도 검토한다. 아직 확정 구현 범위가 아니며, 채택 시 기존 areaRange를 수정하고 확인 근거·작성 주체를 남기는 방향을 제안한다. 주소만으로 특정 세대의 정확 면적을 확정하지 않는다.

### 3.5 층수 — 선택적 후속안, 현재 미확정

확정 시 step 3에 `floor` 정수 필드를 추가하고 기존 Room.floor와 연결한다. 프런트가 302호→3, 1602호→16, B101호→-1로 추정한 뒤 등록자가 확인·수정한다. 호수 문법 전체를 무조건 나누기 100으로 처리하지 않는다. 추정 불가·미확인은 null, 0은 사용하지 않는 안이다. 허용 범위 및 필수 여부는 미확정이므로 아직 DTO에 강제하지 않는다.

### 3.6 가격·소개 재사용

step 8의 월세 정수 1~~100,000,000원, 보증금·관리비 정수 0~~1,000,000,000원 검증을 유지한다. null과 0을 구분한다. submit 및 approval에서도 검사한다. 매물 설명·생활 조건·최소 거주 기간은 기존 필드를 사용한다.

집주인 소개는 기존 User.introduction 및 PUT /me를 재사용한다. 별도의 '매물 집주인 소개' 저장 필드를 만들지 않는다. 공개용 host 응답에는 필요한 프로필만 매핑하고 사용자 원본 객체·연락처·인증 정보를 그대로 반환하지 않는다.

## 4. 관리자 소제목

Room에 nullable `subtitle` 추가 제안. 기본 null, trim 후 1~100자 일반 텍스트. 관리자 room/super만 수정 가능. 호스트 등록 DTO에 포함하지 않는다.

```http
PATCH /admin/rooms/:id/subtitle
Content-Type: application/json

{"subtitle":"공릉역 도보 7분"}
```

- 성공 200: `{ "id": "매물 UUID", "subtitle": "공릉역 도보 7분" }`.
- `{ "subtitle": null }`은 삭제. 키 생략·빈 문자열·공백·100자 초과·알 수 없는 필드는 400. 공개에는 HTML로 해석하지 않는다.
- 401 인증 없음/만료, 403 권한 없음, 404 대상 없음, 신규 draft 대상은 기존 관리자 정책에 맞춰 409 제안.
- 기존 가격·description·공개 상태는 변경하지 않는다. 관리자가 검수하며 입력하고 저장 후 기존 목록/상세 캐시를 갱신한다.
- 기존 PATCH /admin/rooms/:id는 가격 3종이 필수이며 description 생략 시 삭제될 수 있다. 소제목 단독 저장에 이를 재사용하면 데이터 손실 위험이 있어 전용 API를 제안한다.
- 감사 로그 action `updateRoomSubtitle` 제안. 관리자·대상·변경 전후를 기록한다. 제출자에게 편집 권한을 주지 않는다.
- 소제목 미입력이어도 게시 가능하게 하는 안을 제안한다. 기존 매물은 null이며 UI에서 해당 줄을 생략한다.

## 5. 조회 응답

legacy flat과 registrationContractVersion=2의 중첩 응답은 현재 구분을 유지한다. 인원·면적을 v2 중첩 data와 또 다른 상세 필드에 중복 저장하지 않는다.

| 데이터         | 목록 item 추가/통일             | v2 상세                                      |
| -------------- | ------------------------------- | -------------------------------------------- |
| 제목           | `title: string` (새 기준 매물)  | 같은 서버 생성 제목                          |
| 소제목         | `subtitle: string \| null`      | 최상위 subtitle 추가 제안                    |
| 유형           | `buildingType`                  | `data.location.buildingType`                 |
| 지역           | `region`, `addressRegion`       | 권한별 location에 공개 지역과 정확 주소 분리 |
| 현재 거주 인원 | `residentCount: number \| null` | `data.household.residentCount`               |
| 입주 가능 인원 | `roomCapacity: enum \| null`    | `data.preferences.roomCapacity`              |
| 면적           | 목록 필수 추가 아님             | `data.household.areaRange`                   |
| 집주인         | 목록에 추가하지 않음            | 회원에게 공개용 host DTO 반환                |

목록의 사진·가격 등 공개 필드는 6절의 미확정 정책을 확정한 뒤 적용한다. 새 데이터에는 필수값이 있지만 legacy에는 null이 있을 수 있어 읽기 스키마에서 0이나 임의 문자열로 조작하지 않는다. 오류 응답을 '정보 없음'으로 바꾸지 않는다.

## 6. 회원별 공개 정책

현재는 익명/로그인/예약 승인/계약의 4단계이며 isAddressDetailHidden 예외도 있다. 새 정책은 단순 프런트 가림이 아니라 서버 serializer 및 접근 정책 변경이다.

| 항목                                     | 비회원              | 정상 로그인 회원      |
| ---------------------------------------- | ------------------- | --------------------- |
| 제목·동까지 지역                         | 공개                | 공개                  |
| 도로명 주소·건물 위치(동·호수 제외)      | 응답에서 제외       | 공개                  |
| 건물 동·호수(addressDetail)              | 응답에서 제외       | 응답에서 제외         |
| 층수                                     | 공개 범위 별도 확인 | 공개                  |
| 정확한 좌표·위치 안내                    | 응답에서 제외       | 공개                  |
| 상세 계약정보                            | 응답에서 제외       | 공개                  |
| 집주인 공개 프로필                       | 응답에서 제외       | 공개                  |
| 사진·목록 가격·소제목·생활 조건          | 범위 미확정         | 해당 공개용 정보 제공 |
| 관리자 메모·본인확인 원본·내부 연락 정보 | 제외                | 제외                  |

'전부 공개'를 내부 관리자 자료까지 공개하는 의미로 확장하지 않는다. 잘못된 JWT·비활성 회원은 기존대로 401이며 익명으로 다운그레이드하지 않는다. 매물 비공개/없음은 404 유지.

공개 제한 응답은 기존 discriminator 구조에서 전용 preview DTO로 검증한다. 비회원 응답에 누락되는 상세 필드를 필수로 파싱하지 않는다. 회원용 응답이 CDN/BFF/서버 캐시에 익명과 공유되지 않게 하고, 로그아웃 시 클라이언트 캐시에서도 회원 상세를 제거한다. 주소는 HTML·스크립트 초기 데이터·지도 요청에도 새지 않게 검증한다.

관리자 주소 숨김 기능은 이번 UI·개발 범위에서 제외한다. 기존 API는 삭제하지 않는다. 기존 true 데이터의 동작은 임의로 해제하지 않으며 새 일반 회원 응답은 이 플래그와 관계없이 동·호수를 항상 제외한다.

## 7. 탐색·메인 공통 검색 제안

GET /rooms를 재사용한다. 별도 메인 전용 매물 저장소/API를 만들지 않는다.

| Query 제안                | 규칙                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `q`                       | 검색 대상·학교/역 연관 방식 모두 추후 결정. 지역·제목 검색도 확정 계약으로 구현하지 않음 |
| `legalDongCode`           | 동 단위 정확 일치. 검증된 코드 사용                                                      |
| `sidoCode`, `sigunguCode` | 서버 기준 지역 코드와 정확 일치. 기존 UI 코드 체계와 매핑 확정 필요                      |
| `buildingTypes`           | 반복 키 배열 예: buildingTypes=apartment&buildingTypes=officetel. 항목 간 OR             |
| `roomCapacity`            | one/two/threeOrMore 구간 정확 일치. 기존 UI의 '3명 이상'과 연결                          |

서로 다른 확정 필터는 AND, 유형 배열 내부는 OR로 제안한다. 잘못된 코드·enum·충돌하는 상하위 지역은 400 제안. 자유 검색 q의 의미·정규화·학교/역 관계는 추후 확정하며 이 절의 q는 구현 요청에서 제외한다.

기존 가격(원)·성별·availableFrom·minStayMonths·immediateOnly 필터와 페이지 응답 `{items,total,page,limit,totalPages}`는 유지한다. total은 동일 조건의 중복 없는 매물 수여야 한다. 동일 정렬값에는 id 등 안정적인 보조 정렬을 적용한다.

기존 region 쿼리는 백엔드 문서상 문자열 부분 일치이며, 프런트 주석의 '정확 일치'와 다르다. 새 코드 필터로 전환하되 legacy region 호출은 이행 기간 유지한다. q/코드 필터와 legacy region 동시 전송은 거부하는 안을 제안한다.

메인 자유 검색은 q 계약 확정 후 연결한다. 지역 탭은 구조화된 지역 코드로 연결한다. 신규 매물의 최초 게시일 정렬, 추천순 제거는 기존 제안이며 확정 여부를 별도 표시한다.

## 8. 검증·오류 계약

- 기존 HttpErrorResponseDto 형식 유지. 임의의 새 에러 envelope를 만들지 않는다. 필드별 오류 식별자를 기존 형식으로 제공할 수 있는지 구현 시 대조한다.
- 400: 값 형식·필수 데이터 누락·유형/지역 불일치·가격 범위 오류.
- 401/403/404: 기존 인증·권한·소유권 은닉 정책 유지.
- 409: draft version 충돌, 제출/게시 상태 충돌. 공개 승인 시 데이터가 새 기준에 미달하면 상태를 바꾸지 않고 오류 반환.
- 5xx/503: API·외부 시스템 실패. 정보 없음이나 빈 검색 결과로 바꾸지 않는다.
- 주소·가격이 부족한 기존 예시를 읽는 동작과 새 운영 매물 제출을 분리한다. 기존 오류 보류를 이유로 허위 주소·0원을 채우지 않는다.

## 9. 이행·개발 순서 및 검증 기준

1. 서버에 nullable subtitle/region 저장 구조와 읽기 호환을 추가한다. 기존 데이터는 추정 backfill 금지. 기준 코드 출처와 동기화 방식을 정한다.
2. enum을 확장하고 새 DTO·serializer·검색을 제공한다. DB enum에서 villa/other를 즉시 삭제하지 않는다.
3. 프런트 타입/Zod/BFF query allowlist·등록 autosave·관리자 UI·목록 매퍼를 함께 연결한다.
4. 기존 active draft와 게시 매물을 조사한 뒤 신규 제출·재게시 필수 검증을 활성화한다. 기존 draft는 재입력 안내로 복구 가능하게 한다. 제출·승인 모두 검증해 우회 경로를 막는다.
5. 기존 저장 정책과 의미가 호환되지 않는 변경은 계약 버전 상향 여부를 판단한다. registrationContractVersion=2를 유지한 채 legacy shape를 조용히 변경하지 않는다. 공개 DTO 변경도 클라이언트와 배포 순서를 맞춘다.
6. 새로운 enum을 저장한 뒤 구버전 클라이언트로 단순 롤백할 수 없음을 고려한다. 새 쓰기 중단·읽기 호환 유지·새 필드 보존을 복구 전략으로 사용한다.

시험 매물 2~3개로 다음을 검증한다.

- 등록 → 저장 재조회 → 제출 → 관리자 소제목 저장 → 승인 → 메인·탐색·상세에서 동일 값 확인.
- 현재 거주 2명/입주 가능 1명이 각각 유지되고, 3명 이상이 숫자 3으로 축소되지 않음.
- 20평대가 집 전체 면적으로 표시되고 방 크기와 뒤섞이지 않음.
- 소제목 수정·삭제가 가격·매물 설명을 바꾸지 않으며 일반 회원 수정은 거부됨.
- 사용자 요청에 따라 이번 실매물 시험에서 주소·가격 누락 시나리오는 제외한다. 제출·게시의 필수 검증 정책 자체는 유지한다.
- 지역·유형·인원·가격·입주일·기간·성별의 조합과 total/초기화/페이지 이동 일치.
- 회원/비회원 응답 및 로그아웃 후 HTML·캐시·지도에서 공개 정책 일치.
- 상세 오류 수정 보류에 따라 정확 주소가 있는 시험 매물로 연결 검증. 누락 주소 상세 오류 해결을 완료했다고 보고하지 않음.
